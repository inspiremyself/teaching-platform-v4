### 2.2 要解决的问题

1. 平台无法在后台开通第二所学校，也无法停用学校；学校 `status` 已存在但没有维护入口。
2. 多校并存下 6 张教学业务表尚无 `school_id`，需由 1B 收口；新增第 4 角色时须保证平台超管不进入任一学校的组织数据范围。
3. 现有三角色登录、单会话、JWT 契约稳定，任何改造都不能破坏它们与越权校验。

## 3. 目标与成功标准

### 3.1 目标

1. 平台运营人员能用一个账号开通、停用多所学校，并为新学校创建首位校管。
2. 平台运营人员只维护学校租户本身与阶段 3 的平台内容授权，不进入任何学校的组织管理页；学校组织数据仍由本校校管维护。
3. 平台超管访问任何学校组织端点、教师端与学生端端点均被拒绝；停用学校后该校账号不可登录；不泄露学校存在性。
4. 现有三角色登录、单会话、演示账号、10 条既有冒烟路由（另新增平台超管 1 条）与全部既有测试行为不变。

## 4. 角色与权限

### 4.1 用户故事

| 角色 | 故事 |
|---|---|
| 平台超管 | 登录后进入「学校管理」，看到全部学校及状态；开通新学校时填写学校名称、编码、首位校管账号与初始密码；发现学校需停止使用时将其停用；阶段 3 可制作平台课件与题目并授权给指定学校集合使用。**不进入任何学校的教师 / 学科 / 班级 / 学生管理页** |
| 学校管理员 | 与现网完全一致：登录即进入本校 `/admin/dashboard`，只见本校数据；不受平台超管功能影响 |
| 教师 / 学生 | 与现网完全一致；平台超管账号不能访问教师端与学生端能力 |

### 4.2 权限矩阵（完整枚举）

| 角色 | `permissions` |
|---|---|
| `SCHOOL_ADMIN` | `SCHOOL_READ`, `SCHOOL_WRITE`, `TEACHER_READ`, `TEACHER_WRITE`, `CLASS_READ`, `CLASS_WRITE`, `STUDENT_READ`, `STUDENT_WRITE` |
| `TEACHER` | `CLASS_READ`, `LAB_WRITE`, `HOMEWORK_WRITE`, `EXAM_WRITE`, `ANALYSIS_READ` |
| `STUDENT` | `MATERIAL_READ`, `LAB_READ`, `HOMEWORK_READ`, `EXAM_READ`, `SCORE_READ` |
| `PLATFORM_ADMIN` | `SCHOOL_READ`, `SCHOOL_WRITE`, `SCHOOL_PROVISION` |

现有 6 个 admin controller 的类级注解保持现网 `hasRole('SCHOOL_ADMIN')` 一字不改，平台超管访问这些端点返回 403；新增第 7 个 `PlatformSchoolController` 用 `hasRole('PLATFORM_ADMIN')`；教师端、学生端端点注解保持三角色原状。`GET/PUT /api/v1/admin/school`（本校信息）仍仅 `SCHOOL_ADMIN` 可用，平台超管调用返回 403（沿用现网 AccessDenied 处理）。

### 4.3 平台超管可达端点与默认拒绝

平台超管可达端点按「`SecurityConfig` permitAll + 现有 `@PreAuthorize` 角色注解」唯一确定：① `POST /api/v1/auth/login`（permitAll，不构造 `CurrentUser`）；② 已登录通用 4 条 `POST /api/v1/auth/logout`、`GET /api/v1/auth/me`、`PUT /api/v1/auth/profile`、`POST /api/v1/auth/change-password`；③ 平台级 3 个端点 `GET /api/v1/admin/schools`、`POST /api/v1/admin/schools`、`POST /api/v1/admin/schools/*/status`（`PlatformSchoolController` 类级 `hasRole('PLATFORM_ADMIN')`）。1A 共 8 个端点（含 permitAll 登录），按端点数计。阶段 3 按总纲 D07 追加 `/api/v1/admin/platform-content/**`（同一类级注解，平台内容制作与按学校集合授权不依赖学校上下文），1A 不实现。其余 `/api/v1/**`（含 6 个 admin controller、教师端、学生端）一律由现有角色注解拒绝，返回现网 403。内容授权表单里的 `school_id` 属 `content_share_grant` 数据字段，与本清单无关。

## 5. 功能需求

### FR-1 新增平台超管角色与演示账号

- `UserRole` 增加 `PLATFORM_ADMIN`；`V25` 含且仅含两条 SQL：① `ALTER TABLE sys_user ${alterModifyColumn} school_id BIGINT NULL;`（复用 `V18` 范式，不改 `FlywayPlaceholdersConfig`）；② 写入显式 `id=6` 的 `platform9001` / `123456` / `PLATFORM_ADMIN` / `school_id` 列写 `NULL` / `ACTIVE`（现网种子已占用 `id=1`–`5`）。`V25` 的 INSERT 完整列清单与口令编码形态由 1A 独立技术方案写死，本文只定 `school_id` 为 NULL、账号唯一与 `id=6`。三角色历史行 `school_id` 取值不变，`uk_sys_user_school_username` 不变、不加部分索引 / 生成列 / DB CHECK；`SysUser` 实体该列改 `nullable = true`（总纲 §4）。
- 登录走现有 `POST /api/v1/auth/login`，`role=PLATFORM_ADMIN`，不填 `schoolCode`；登录后直达 `/admin/schools`。
- 登录响应对 4 个角色同形且一字不变（现网登录响应本就不含 `schoolId`），仍用 `Map.of`；`GET /api/v1/auth/me` 对 `PLATFORM_ADMIN` 不写 `schoolId` / `schoolName` 两个键，其余三角色响应字段一字不变（实现见 FR-4）。
- `DemoAccountProdGuard` 的 prod SQL 唯一形态写死为 `WHERE (school_id = 1 OR school_id IS NULL) AND status = 'ACTIVE' AND username IN ('t9001','20260001','20260002','admin9001','t9002','platform9001')`。不得只把 `platform9001` 追加进原 `username IN` 清单（原 `WHERE school_id = 1` 会排除 NULL 行），也不得删掉 `school_id = 1` 条件（多校同名账号会被误禁用）。

### FR-2 学校列表与开通

- `GET /api/v1/admin/schools` → `List<SchoolItem>`（`id/name/code/status/adminUsername/createdAt`），按 `id` 升序；`adminUsername` 取该校 `role='SCHOOL_ADMIN'` 中 `id` 最小的用户名，无则空串。
- `POST /api/v1/admin/schools` → `CreateSchoolRequest(name, code, adminUsername, adminPassword)`；一次事务内创建 `ACTIVE` 学校 + 该校首位 `SCHOOL_ADMIN`（`school_id=新学校 id`、`ACTIVE`、初始口令由 `PasswordEncoder` 编码），返回 `SchoolItem`。
- 校验：`name` 非空且 ≤ 128 字符、`code` 非空且 ≤ 64 字符、`adminUsername` 与 `adminPassword` 非空（对齐 `V13` 的 `school.name VARCHAR(128)` / `school.code VARCHAR(64)`）；编码已存在 → `40904`「学校编码已存在」；该校已存在同名账号 → `40905`「该校已存在同名账号」；参数校验失败 → `40000` / `40001`。
- 学校编码全局唯一保持不变；`id=1` 演示学校不参与开通。

### FR-3 学校停用与启用

- `POST /api/v1/admin/schools/{schoolId}/status` → `UpdateSchoolStatusRequest(status)`，取值 `ACTIVE` / `DISABLED`。
- `DISABLED`：不清数据、不删用户；该校所有账号登录返回 `40103`；会话表保持不变。
- 登录侧校验写死在 `AuthService.login(LoginRequest)` 内：在现有 `user.getStatus() != ACTIVE` 校验之后、密码校验之前追加一步——`user.getSchoolId() == null` 时**跳过学校校验**（平台超管，不得调用 `schoolRepository.findById(null)`）；否则用已注入的 `schoolRepository.findById(user.getSchoolId())` 取学校，`status == DISABLED` 或学校记录缺失时写 `logLoginFailure(user.getId(), user.getSchoolId(), request)` 并抛 `40103`，文案沿用现网 `LOGIN_DISABLED_MESSAGE`「该账号已被停用，请联系管理员」，不改文案、不新增错误码、不单独暴露学校存在性。不改 `findAllByUsernameAndRole` 与 `schoolCode` 消歧顺序、不改会话与 JWT 链路。
- `id=1` 禁止停用 → `40028`「演示学校不可停用」；学校不存在 → `40400`「学校不存在」。

### FR-4 平台超管数据边界与审计

- `JwtAuthenticationFilter` 构造 6 组件 `CurrentUser` 时直接传 `user.getSchoolId()`，不写按角色置 `null` 的分支；平台超管 DB 值为 NULL，`CurrentUser.schoolId` 因此为 NULL；三角色取值与现网完全一致，会话状态、`KICKED` 优先与过期逻辑一字不改；`CurrentUser` 组件数与便捷构造不变。
- `AuthService.toUserProfile(SysUser user)` 保持单参，两个调用点（`getCurrentUserProfile` / `updateProfile`）不改；方法体内仅当 `user.getSchoolId() != null` 时才 `profile.put("schoolId", ...)` 并 `schoolRepository.findById(...)` 取 `schoolName`，为 `null` 时两个键都不写（前端 `User` 两字段可选，平台超管页面不读取学校信息）；不得对 null 调用 `findById`。
- **平台超管**登录审计（`SecurityAuditEvent` 取 `saved.getSchoolId()`）写 NULL，平台超管登录失败审计 `logLoginFailure(user.getId(), user.getSchoolId(), request)` 同样写 NULL；三角色登录成功 / 失败审计沿用现网 `user.getSchoolId()` 取值，停用学校账号的失败审计按 FR-3 写该校 id、本节不改三角色口径。平台超管业务操作走 `AuditLogService.log(currentUser, ...)`，`audit_log.school_id` 写 NULL（`V18` 已可空），开通 / 停用学校的目标学校 id 写入 `detail_json.targetSchoolId`；`http_access_log.school_id` 同理写 NULL（`V17` 已可空）。平台超管登录审计与业务审计口径统一，不出现学校 id `1`。

### FR-5 平台超管隔离与默认拒绝

- 平台超管 `schoolId` 恒为 `null`，不进入任何学校数据范围；6 个 admin controller 的类级 `hasRole('SCHOOL_ADMIN')` 与 6 个 admin service 的按校过滤一字不改，跨校资源 id 访问沿用现网 `40400` / `40300`，不泄露存在性。
- `POST /api/v1/admin/schools` 开通与 `PUT /api/v1/admin/school` 改名**不是兄弟操作**：前者仅 `PLATFORM_ADMIN`（`PlatformSchoolController` 类级注解），后者仅 `SCHOOL_ADMIN`（`AdminSchoolController` 类级注解，现网不动）；二者不共享角色白名单、不共享 `CurrentUser.schoolId()` 数据范围校验。
- 平台超管不能访问教师端与学生端端点；其余 `/api/v1/**` 按 §4.3 由角色注解拒绝。
- 业务操作审计与登录审计口径按 FR-4 执行。
