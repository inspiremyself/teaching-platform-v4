### 2.2 问题清单

| 编号 | 现象 | 影响 |
|---|---|---|
| P1 | 阶段之间靠用户逐句推动：方案自查、编码、实现自查都要人肉 `@` 或说口令 | 流程规范写得再细也不会自己跑；用户是实际「调度器」 |
| P2 | 收敛判定靠人记：K>2 必须再开一轮，但没人提醒就可能被跳过 | 未收敛即编码/声称可验收的质量风险 |
| P3 | 门禁命令靠现场拼：lint/test/build、重启、healthcheck 每次手工组合 | 端口占用、启动顺序等瞬态错误反复出现；结果不可结构化判断 |
| P4 | 交付动作靠人发指令：commit/push 与验收清单生成都需单独交代 | 报告口径不稳定；但全自动 push 风险不可接受 |
| P5 | Hooks 能力被误解为「万能自动化」：实际为 CLI Beta、IDE 未确认，且与 11-12 已定稿方案的权限边界冲突 | 若作为主力，方案落地即卡壳或与现网冲突；本期零新增 Hook，守卫沿用现网 `permissions.deny` |
| P6 | 浏览器验收缺工具（`playwright-cli` 未安装）且无清单模板 | 验收清单未落到可复用模板，易漏项；本期由 FR-14 交付清单模板 + A11 覆盖 |

## 3. 目标与非目标

### 3.1 目标

1. 用户一句「完整实施 xxx」即可自动推动方案收敛 → 编码 → 实现收敛 → 门禁 → 环境验收 → 展示交付报告，全程无需逐步指令；提交与推送由用户自行执行。
2. 自查轮次与收敛门槛由技能硬性执行，K>2 自动进入下一轮，不依赖用户记忆。
3. 确定性动作（lint/test/build、服务启动/探活、healthcheck）脚本化、幂等、输出结构化结果。
4. 交付阶段自动生成 commit message 建议、diff 摘要与验收清单并展示，随后流程结束；提交与推送由用户自行执行。
5. 全部自动化资产遵守「引用而非复制」，不制造第二份规范或第二份流程说明。

### 3.2 非目标（明确否决）

| 非目标 | 结论与理由 |
|---|---|
| 新增任何 Hook 或用 Hooks 做主编排 | 否决；事件钩子无「阶段/轮次」语义，无法判定收敛，CLI Beta / IDE 未确认，且与 11-12 已定稿方案 D4/D5 冲突（D8） |
| 自动 commit/push、自动改方案定稿状态 | 否决；不可逆远程操作必须人工确认，现网 `permissions.deny` 已禁 `git push`（D7） |
| 修改 `.cursor/rules/*.mdc`、新建规范文档 | 否决；违反单一事实来源总纲（D9） |
| 修改业务前后端代码、API、DTO、Flyway、权限、`data/` | 否决；本期是研发工具链建设，不是业务功能 |
| 合并或重写 `self-review-and-fix`、`local-data-backup` | 否决；两者已成熟且需独立触发（D12） |
| 引入新 npm 依赖、新测试框架、截图快照基线 | 否决；沿用现有 vitest 源码断言与 shell 脚本 |
| 用 mock 页面/假 API 演示「全流程跑通」 | 否决；违反项目真实系统约束与 D11 |
| 放宽备份门禁或收敛标准以换取「一键全自动」 | 否决；自动化不能降低质量门槛（D13） |
| 依赖 Hooks 或项目级 settings.json 才能工作 | 否决；本期零新增 Hook、零新建 settings 文件，守卫沿用现网用户级配置（D8/D10） |

## 4. 需求明细

### 4.1 P1：编排技能与门禁脚本

**FR-1 编排技能（D2/D4/D5/D12/D13）**：新建 `.cursor/skills/feature-delivery-pipeline/SKILL.md`，含 YAML frontmatter（`name`、`description`）与 Markdown 正文。`description` 写死触发语义：「当用户说『完整实施 / 按方案开发 / 走完研发流程 / 从需求到交付』，或要求自动推进技术方案→编码→自查→验证时使用」。正文必须：① 首节写明「规范来源为 `feature-dev-workflow.mdc`，自查执行入口为 `.cursor/skills/self-review-and-fix/SKILL.md`，本技能不复制其条款」；② 写死 Stage 0–6 状态机表（FR-2～FR-8）；③ 写死「先 Read 被 invoke 技能的 SKILL.md 全文再执行」；④ 写死「每阶段结束用 `todo_write` 标记状态，未达门槛禁止推进」；⑤ 明确「语义判断不由脚本替代，禁止为推进阶段放宽 K 门槛」。

**FR-2 Stage 0 输入判定（D4）**：按「已有 PRD / 已有技术方案 / 已有实现 diff」三态决定起点：缺 PRD 时提示用户补充需求输入但不臆造 PRD；缺技术方案时进入 Stage 1 起草；已有已定稿方案且无实现 diff 时进入 Stage 2；已有实现 diff 时进入 Stage 3。判定结果写入会话任务清单。

**FR-3 Stage 1 方案收敛（D5）**：起草或修订 `docs/技术方案/YYYY-MM-DD-<主题>.md` 后，invoke `self-review-and-fix` **方案模式**；按技能 §2 逐轮自查、修复、汇报；K>2 必须再开一轮；收敛后文首标「已定稿（决策写死，可直接编码）」并更新 §修订记录。**未收敛禁止进入 Stage 2**。

**FR-4 Stage 2 编码（D4/D13）**：严格按已定稿方案列出的文件与能力改动；按 `code-conventions.mdc` §2 路由读对应细则；不改方案外文件；遇 Flyway / 清库 / 覆盖库先过备份门禁（D9 的上位约束），不提供跳过路径。

**FR-5 Stage 3 实现收敛（D5/D12）**：编码完成后 invoke `self-review-and-fix` **实现模式**；按技能 §3 对照 git diff 扫契约/交互/竞态/资源/边界/范围外/规范/测试八类漏项；列出编号问题点并修复；K>2 再开一轮；**未收敛禁止进入 Stage 4**。Stage 4 门禁 FAIL 与 Stage 5 **代码/契约类** FAIL 时回到本阶段，问题点重新计数；Stage 5 环境类 FAIL 按 FR-7 暂停提示，不回本阶段。

**FR-6 Stage 4 门禁（D6）**：调用 `scripts/dev/gate.sh`，该脚本按改动范围串起 `cd frontend && npm run lint && npm test && npm run build` 与 `cd backend && ./mvnw test`（无对应改动的类型可跳过但该跳过须在输出中标注）；统一输出 `PASS` 或 `FAIL` 摘要与退出码。技能只读退出码：FAIL 回 FR-5，PASS 进 FR-7。禁止把命令输出直接当作「已通过」的证据而不看退出码。

**FR-7 Stage 5 环境验收（D4/D6）**：调用 `scripts/dev/env-up.sh`，该脚本执行端口检查（默认后端 8080 / 前端 5173）、按「未就绪则启动、已就绪则跳过」的写死规则调用 `scripts/path-b/backend.sh` 与 `scripts/path-b/frontend.sh`、等待就绪、调用 `scripts/common/healthcheck-login.sh`；启动顺序为**后端先就绪再前端**；PASS 进 FR-8。失败按原因写死分流：① 环境类（端口占用、服务无法启动、Vite 代理不可达）→ 脚本输出 `FAIL` + 原因 + `[ENV]`，技能**暂停并提示用户处理**（如停掉占用进程），用户处理后从 Stage 5 重试，不回 Stage 3；② 代码/契约类（服务启动后 healthcheck 登录失败、接口 4xx/5xx）→ 输出 `FAIL` + `[CODE]`，技能回 FR-5 重新计问题点。技能不得自行 `kill` 进程或改端口配置；两种失败均不得静默跳过。

**FR-8 Stage 6 交付（D7）**：调用 `scripts/dev/delivery.sh --prepare`，生成 commit message（写「为什么」）、`git diff --stat` 摘要、按方案 §验收标准生成的验收清单模板（含本期无法自动执行的浏览器验收项与待人工项）；展示给用户后**流程结束**，提交与推送由用户自行执行（现网 `permissions.deny` 已禁止 AI 执行 `git push`）。脚本不提供 `--push` 子命令。清单模板与 `docs/运维文档/` 的关系见 FR-13。

**FR-9 gate.sh 规格（D6）**：位于 `scripts/dev/gate.sh`；默认（无参数）按 `git diff` 判定改动侧并只跑对应命令，无改动侧打印 `[SKIP]`；显式 `--frontend` / `--backend` / `--all` 时**强制跑指定侧，不做跳过判定**（`--all` 即两侧全跑）。三种模式互斥，不叠加。幂等（重复执行不产生副作用）；所有子命令退出码汇总，任一非 0 则脚本非 0；输出固定前缀 `[PASS]` / `[FAIL]` / `[SKIP]`；不改任何文件；超时与失败原因写入 stdout 供技能读取。遵守 `ops-docs-and-scripts.mdc`。

**FR-10 env-up.sh 规格（D4/D6/D11）**：位于 `scripts/dev/env-up.sh`；幂等（服务已就绪则报告 ALREADY_RUNNING 而非重复启动）；端口占用时报告占用方 PID 并退出非 0，不擅自 kill，输出含 `[ENV]` 标记；healthcheck 登录失败等服务内错误输出含 `[CODE]` 标记；按「后端 → healthcheck → 前端 → HTTP 探活」顺序；沿用既有脚本与 `SERVER_PORT` / `VITE_API_TARGET` 约定；输出 `[PASS]` / `[FAIL]` / `[ALREADY_RUNNING]`，`[FAIL]` 必带 `[ENV]` 或 `[CODE]` 之一；不使用 mock 服务。

**FR-11 delivery.sh 规格（D7）**：位于 `scripts/dev/delivery.sh`；**只实现 `--prepare` 一个子命令**，读取 `git diff --stat` 与方案验收标准，输出 commit message 建议、diff 摘要与逐条验收清单到 stdout，不写文件、不执行任何 git 写操作。脚本**不实现 `--push` / `--commit` / `--add`**；用户后续自行提交与推送。报告中的 commit message 建议遵循「写为什么」。

### 4.2 P2：显式入口与文档

**FR-12 `/dev-flow` 自定义指令（D3）**：在 CodeBuddy 自定义指令界面创建项目级指令 `dev-flow`，提示词正文写死「读取并执行 `.cursor/skills/feature-delivery-pipeline/SKILL.md`，需求：`$ARGUMENTS`」；描述写「从需求/技术方案自动推进到自查、门禁与交付」。不得在指令正文里复制 SKILL.md 的阶段表（D9）。

**FR-13 脚本运维说明（D6/D9）**：在 `docs/运维文档/` 新增带日期前缀的说明文档（如 `2026-11-25-研发工作流自动化脚本说明.md`），只记录三个脚本的用法、参数、退出码与示例；不复制规范条款、不替代 rule。脚本本身的可执行行为以代码为准。

**FR-14 交付清单模板（D7/P6）**：`delivery.sh --prepare` 生成的验收清单须按方案 §验收标准逐条列出编号与验收项，并显式标注「需浏览器人工验收」与「本次已自动验证」两类状态；本期无法执行浏览器验收时如实列出待办，不标为通过。

### 4.3 守卫能力（沿用现网，零新增资产）

**FR-15 只读守卫（D8/D10）**：本期**不新增 Hook、不创建项目级 `.codebuddy/settings.json`**。危险命令拦截沿用 11-12 技术方案已落地的用户级 `permissions.deny`（7 条，含 `Bash(rm:*)` 与 `Bash(git push:*)`）；自查收敛与门禁记录由技能内 `todo_write` 状态自检，不依赖 Hook 读取会话外状态。任何针对本工具的 hook 配置、settings 文件变更均属范围外。

## 9. 已否决方案

| 否决项 | 原因 |
|---|---|
| 只做一个「大而全」技能 | 把 lint/test/build、重启等确定性动作交给模型现场拼命令，不可靠且不可结构化判定；违反 D6 |
| 只用 Hooks / 事件回调，或新增 Hook 增强 | Hooks 无阶段与轮次语义，无法判定自查收敛；CLI Beta 且 IDE 支持未确认；与 11-12 已定稿方案 D4/D5 冲突（D8） |
| 只用自定义斜杠指令 | 自定义指令是入口不是执行器，文档未确认可调用技能；无法承载多轮收敛判断（D3） |
| 只用自定义 Agent | 与现有 3 个技能 + rule 体系重复建设，维护成本高；官方「更高程度自动化」描述不等于可直接替代既有工作流 |
| 自动 commit/push、自动改文件 | 不可逆远程操作与未审计写操作风险不可接受，且现网 `permissions.deny` 已禁 `git push`（D7） |
| 把 rule 条款复制进 SKILL.md / 指令正文 | 制造第二份事实来源，违反仓库总纲「规范细则只写在 `.cursor/rules/*.mdc`」（D9） |
| 用 MCP 接入外部服务作为本流程主力 | 本流程对象是本地仓库、脚本与既有技能；MCP 增加配置面而无收益 |
| 为「全自动」放宽 K 门槛或备份门禁 | 质量门禁不可交易（D13） |
