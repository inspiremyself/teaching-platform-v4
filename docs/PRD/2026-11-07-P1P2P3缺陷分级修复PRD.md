本文只处理 P1/P2/P3。当前会话确认的 4 个 P0 不在本文范围，另行跟踪：

## 3. 阶段一：P1 安全与租户隔离

### FR-1 跨校同名账号登录（S1）

**现象**：两个学校存在相同 `username + role` 时，登录接口抛 `IncorrectResultSizeDataAccessException`，返回 500；即使不抛异常，也无法判断应登录哪个学校。

**证据**：`auth/service/AuthService.java#L66-L80` 使用 `findByUsernameAndRole` 返回 `Optional`；`V13__school_organization_phase1.sql#L17-L19` 已删除全局 username 唯一约束，改为 `(school_id, username)`。

**决策**：

1. `LoginRequest` 新增可选组件 `schoolCode`（学校编码，对应 `school.code`）。保留现有 3 参与 4 参构造，分别委托为 `(username, password, role, false, null)` 与 `(username, password, role, forceLogin, null)`；既有调用与测试不改语义。
2. `SysUserRepository` 新增 `List<SysUser> findAllByUsernameAndRole(String username, UserRole role)`；原 `findByUsernameAndRole` 保留给其它调用点。`SchoolRepository` 新增 `Optional<School> findByCode(String code)`。
3. 登录查询改用 `findAllByUsernameAndRole`：
   - `schoolCode` 非空：先用 `SchoolRepository.findByCode` 解析 `schoolId`，再按学校过滤；学校不存在或过滤后为 0 条 → `LOGIN_ERROR`；仍多于 1 条（脏数据）→ `40903`。
   - `schoolCode` 为空：按全局条数判断；0 条 → `LOGIN_ERROR`；1 条 → 继续；多条 → `40903`「该用户名在多个学校存在，请填写学校编码后重试」。
4. 前端契约：`frontend/src/types/user.ts` 的 `LoginDto` 新增 `schoolCode?: string`，`stores/auth.ts#login` 原样透传。`frontend/src/views/auth/Login.vue` 新增可选「学校编码」输入框，`LOGIN_ERROR_MAP` 增加 `40903: '该用户名在多个学校存在，请填写学校编码'`；命中 `40903` 时展开并聚焦该输入框，不弹二次确认框（40901 的二次确认逻辑不变）。`utils/request.ts` 两处静默列表（成功分支 `#L46`、错误分支 `#L65`）追加 `40903`，避免全局 toast 与行内提示重复。
5. 管理端创建教师/学生沿用现有 `(school_id, username)` 唯一约束，不新增规则。
6. 不新增数据库迁移。

**验收**：

- 单校唯一用户名登录行为不变。
- 两校同名账号：不填学校编码返回 `40903`；填写正确编码后登录成功。
- 填写不存在的编码返回 `LOGIN_ERROR`，不泄露账号是否存在。

### FR-2 课程资料学校隔离（S2）

**现象**：学生 `GET /api/v1/materials` 能看到所有学校 `visibility=ALL` 的资料，并通过 `/materials/{id}/download` 下载。

**证据**：`material/service/MaterialService.java#L29-L34` 学生只按 `visibility=ALL` 查询；`#L82-L93` 下载只校验 `visibility`；`material/entity/CourseMaterial.java#L11-L35` 无学校字段。

**决策**：

1. 新增迁移 `V24__course_material_school_scope.sql`：
   - `ALTER TABLE course_material ADD COLUMN school_id BIGINT NULL;`
   - `UPDATE course_material SET school_id = (SELECT school_id FROM sys_user WHERE id = uploader_user_id) WHERE school_id IS NULL;`
   - `ALTER TABLE course_material ${alterModifyColumn} school_id BIGINT NOT NULL;`（复用双方言占位符）
   - `CREATE INDEX idx_course_material_school_visibility ON course_material (school_id, visibility);`
2. `CourseMaterial` 增加 `schoolId` 字段；`MaterialService.uploadMaterial` 写入 `currentUser.schoolId()`；为 null 时抛 `40000`「账号未绑定学校，无法上传资料」。
3. `CourseMaterialRepository` 新增：
   - `findBySchoolIdOrderByIdDesc(Long schoolId)`
   - `findBySchoolIdAndVisibilityOrderByIdDesc(Long schoolId, MaterialVisibility visibility)`
   - `findBySchoolIdAndUploaderUserIdOrderByIdDesc(Long schoolId, Long uploaderUserId)`
4. 查询口径（`MaterialService.listMaterials`）：
   - 学生：`findBySchoolIdAndVisibilityOrderByIdDesc(schoolId, ALL)`。
   - 教师：`findBySchoolIdAndUploaderUserIdOrderByIdDesc(schoolId, currentUser.id())`。
   - 校管：`findBySchoolIdOrderByIdDesc(schoolId)`，只列本校全部资料；不新增校管资料管理入口。
5. 下载校验（`MaterialService.downloadMaterial`）：先校验 `material.schoolId` 等于 `currentUser.schoolId()`，再执行现有“教师必须是 uploader、其他角色必须 `visibility=ALL`”校验。
6. 历史数据回填依赖 `uploader_user_id → sys_user.school_id`。迁移前统一清理“uploader 不存在或 uploader 未绑定学校”的资料，避免回填 NULL 后 NOT NULL 失败：`DELETE FROM course_material WHERE uploader_user_id NOT IN (SELECT id FROM sys_user WHERE school_id IS NOT NULL);`，并在迁移注释中记录该清理动作。

**验收**：

- A 校学生列表与下载均看不到 B 校资料。
- A 校教师只能看到并下载自己上传的资料。
- 上传后 `school_id` 与上传者一致。
- H2 与 MySQL 两种 profile 均可完成迁移。

### FR-3 实验查重真实化（S3）

**现象**：实验提交后 `plagiarismRate` 恒为 0，查重任务列表没有 `LAB` 记录。

**证据**：`lab/service/LabSubmissionClaimService.java#L48` 是唯一写入点，固定 0；`lab/service/LabService.java#L2113` 的 `submissionRate(answer)` 是单题作答率，不是查重率；`plagiarism_task.business_type` 已支持 `LAB`（`PlagiarismService.java#L245-L252`）。

**决策**：

1. 在 `LabService.submitLab` 完成自动评分与状态刷新后，执行与作业一致的查重：
   - 候选集：同一 `labId` 下状态为 `SUBMITTED` / `GRADED` 且排除当前提交。
   - 文本：拼接该提交全部 `LabStepAnswer.answerText`，空文本跳过。
   - 复用 `LocalPlagiarismService.analyze`。
2. 新增 `plagiarism/service/PlagiarismTaskWriter`，提供 upsert：`write(BusinessType type, Long businessId, Long studentId, double rate, String topMatchSummary, String rawJson)`；内部复用 `PlagiarismTaskRepository.findByBusinessTypeAndBusinessId`，`status` 固定写 `PlagiarismStatus.COMPLETED`，`topMatchSummary` 超过 255 字符时截断。
3. `HomeworkService` 删除私有 `savePlagiarismTask`，改调 `PlagiarismTaskWriter.write`；`LabService` 调用同一 writer，写入 `businessType=LAB`、`businessId=labSubmission.id`。
4. 结果写入 `LabSubmission.plagiarismRate`。
5. 查重异常不阻断提交：捕获异常、记录 `WARN`、`plagiarismRate` 保持 0，不生成任务。
6. 教师实验报告列表/详情统一读取 `LabSubmission.plagiarismRate`；删除 `LabService.submissionRate(answer)` 私有方法及其调用，避免与查重率混淆。
7. 仓储新增 `LabSubmissionRepository.findByLabIdAndSubmitStatusIn`；答案文本用现有 `LabStepAnswerRepository.findByLabSubmissionId` 读取；不新增迁移。

**验收**：

- 同一实验两份高相似提交，后提交者 `plagiarismRate > 0`。
- 查重任务列表出现 `businessType=LAB` 记录，教师可打开详情。
- 不同实验之间不互相比较。
- 查重失败时提交仍成功，响应中的 `plagiarismRate` 为 0。

### FR-4 实验引用资料归属校验（S4）

**现象**：教师可通过 `materialId` 引用任意资料，实验详情会回显该资料的标题/文件名。

**证据**：`lab/service/LabService.java#L1701-L1715` 直接 `setMaterialId`；`#L1767-L1780` 按 id 查资料并回显。

**决策**：

1. `createLab` / `updateLab` 在调用 `applyLab` 前校验：
   - `materialId == null` → 跳过。
   - 资料不存在 → `40000`「资料不存在」。
   - `!Objects.equals(material.getSchoolId(), currentUser.schoolId())` → `40000`「无权限引用该资料」（`Long` 必须用 `Objects.equals`，禁止 `!=`）。
2. 校验放在写实体之前，失败不产生任何变更。
3. 依赖 FR-2 新增的 `CourseMaterial.schoolId`；实施顺序固定为 **FR-2 → FR-4**，FR-2 未合并前不单独合并本项。

**验收**：

- 引用本校资料成功。
- 引用他校资料返回 `400`，实验不落库。
- 引用不存在的 id 返回 `400`。

### FR-5 密码存储与 H2 控制台（S5）

**现象**：密码以 `{noop}` 明文存储；`/h2-console/**` 对所有请求放行。

**证据**：`auth/security/SecurityConfig.java#L39-L42` 返回 `NoOpPasswordEncoder`；`#L30-L33` 对 `/h2-console/**` `permitAll`；`auth/service/AuthService.java#L77` 手动去除 `{noop}` 前缀。

**决策**：

1. `PasswordEncoder` 改为 `PasswordEncoderFactories.createDelegatingPasswordEncoder()`。
2. 登录匹配顺序（必须先判前缀，避免 `DelegatingPasswordEncoder` 对 null id 抛异常）：
   - 哈希以 `{` 开头 → 调 `passwordEncoder.matches(raw, hash)`。
   - 哈希不以 `{` 开头 → 用 `raw.equals(hash)` 做历史明文比较（不得调用 `passwordEncoder.matches`，Delegating 编码器对无前缀 id 会抛 `IllegalArgumentException`），命中后标记 `needsUpgrade=true`。
3. 命中后：`needsUpgrade` 为真，或 `passwordEncoder.upgradeEncoding(hash)` 为真 → 用 BCrypt 重写 `password_hash` 并保存；首次登录即完成升级。
4. 改密、管理员重置密码、新建/导入账号统一写 `{bcrypt}`：`AuthService.changePassword`、`AdminTeacherService.createTeacher`、`AdminStudentService.createStudent` / `importStudents` / `resetPassword` 注入 `PasswordEncoder` 并调用 `encode(raw)`（输出自带 `{bcrypt}` 前缀），删除手工拼接 `"{noop}" + password` 与 `replace("{noop}", "")`。
5. H2 控制台改为条件放行：`SecurityConfig` 注入 `Environment`，用 `h2ConsoleEnabled = environment.acceptsProfiles(Profiles.of("test"))` 判定；仅该值为 true 时把 `/h2-console/**` 加入 `permitAll`，否则该路径落到 `anyRequest().authenticated()`。现有 `frameOptions().sameOrigin()` 与 `csrf.ignoringRequestMatchers("/h2-console/**")` 保持不动。路径 B 的 H2 启动脚本使用 `test` profile（`scripts/path-b/backend-h2.sh`），`application-test.yml` 的 H2 控制台保持开启。
6. 演示账号 `123456` 不在迁移中强制改写，首次登录自动升级。

**验收**：

- 历史 `{noop}` 账号可正常登录，登录后库中变为 `{bcrypt}`。
- 新建账号、改密、重置密码后库中均为 `{bcrypt}`。
- 非 `test` profile 访问 `/h2-console` 返回 401/403。
- 登录失败不泄露“用户存在但密码错误”。

## 4. 阶段二：P2 数据一致性与业务正确性

### FR-6 客观题分数保护（D1）

**现象**：教师调用 `confirmAnswer` 可对客观题直接写分，覆盖自动评分。

**证据**：`exam/service/ExamService.java#L1009-L1027` 未校验题型；同文件 `gradeSubmission` 已显式跳过客观题。

**决策**：

1. `confirmAnswer` 按 `examQuestionRepository.findByExamIdOrderBySortOrder(examId)` 取题项，使用与 `gradeSubmission` 相同的 `resolveQuestionSnapshot` 得到 `QuestionSnapshot`，再调 `examScoringService.isObjective(snapshot.questionType())` 判型；快照缺失时按主观题处理，保持现状。
2. 客观题（单选、多选、判断、填空）：
   - `acceptSuggested=true` → `40000`「客观题不接受推荐分」。
   - 手工 `score` → `40000`「客观题由系统自动评分，不支持手工改分」。
3. 主观题保持现状。
4. 前端 `frontend/src/views/teacher/exams/Results.vue`（L402 调用 `confirmAnswer`）对客观题隐藏“采纳/改分”入口，仅展示自动分；主观题入口不变。

**验收**：

- 客观题调用 `confirmAnswer` 返回 `400`，分数不变。
- 主观题批改与重批不回归。

### FR-7 全客观题作业自动结案（D2）

**现象**：作业提交后固定为 `SUBMITTED`，即使全部题目已有自动分。

**证据**：`homework/service/HomeworkService.java#L444-L466` 提交后未调用 `refreshSubmissionGradeState`；`#L954-L979` 已具备“全部已评分则置 `GRADED` 并写 `score_record`”的能力。

**决策**：

1. `submitHomework` 在 `applyQuestionAnswers` 之后、查重之前调用 `refreshSubmissionGradeState(saved)`。
2. 全客观题且全部有分 → `GRADED`；含主观题 → 保持 `SUBMITTED`。
3. `score_record` 仍只由 `refreshSubmissionGradeState` 写入，不新增写入点。
4. 返回状态使用刷新后的 `submitStatus`。

**验收**：

- 全客观题作业提交后状态为 `GRADED`，并出现在已评分记录中。
- 含主观题作业提交后仍为 `SUBMITTED`，进入待批改队列。
- 重复提交不重复写 `score_record`。

### FR-8 学生完成率口径（D3）

**现象**：分子统计全部可见成绩，分母只统计 `PUBLISHED` 活动，导致完成率超过 100%。

**证据**：`analysis/service/AnalysisService.java#L162-L208`；`VisibleScore` 已包含 `businessType` 与 `businessId`（`StudentScoreVisibilityResolver.java#L42-L46`）。

**决策**：

1. 分母改为 `status IN ('PUBLISHED','CLOSED')` 的三类活动总数。
2. 分子只统计 `businessType + businessId` 命中该集合的可见成绩。
3. 返回值保留一位小数，不做 100 截断；口径正确后自然不超过 100。
4. 不改变成绩可见性规则。

**验收**：

- 活动关闭但成绩可见时，完成率不再超过 100%。
- 未发布草稿不计入分母。
- 三类活动混合场景下完成率与人工核算一致。

### FR-9 查重候选范围收敛（D4）

**现象**：作业查重候选为全库所有已提交/已批改提交，跨作业、跨班级比较，既慢又语义错误。

**证据**：`homework/service/HomeworkService.java#L921-L928` 使用 `findAll()`。

**决策**：

1. 方法签名改为 `buildHomeworkCandidates(Long homeworkId, Long currentSubmissionId)`。
2. 候选集只取同一 `homeworkId` 的 `SUBMITTED` / `GRADED` 提交，排除当前提交。
3. 仓储新增 `findByHomeworkIdAndSubmitStatusIn`。
4. 调用点传 `saved.getHomeworkId()` 与 `saved.getId()`。
5. 不改变查重算法与阈值。

**验收**：

- A 作业提交不会与 B 作业提交产生相似记录。
- 同一作业内相似提交仍能被识别。
- 提交性能不再随全库提交量线性恶化。

### FR-10 非法状态值统一 400（D5）

**现象**：请求传入非法状态字符串时 `Enum.valueOf` 抛 `IllegalArgumentException`，被兜底为 500。

**证据**：`ExamService.java#L182`、`#L400`；`AdminSubjectService.java#L113`；`AdminTeacherService.java#L98`；`AdminStudentService.java#L217`；`LabService.java#L648`、`#L1691`（`parseStatus`，被 create/update/change-status 复用）；`HomeworkService.java#L1072`（`parseStatus`，被 create/update/change-status 复用）。上述 create/update 请求的 `status` 字段均无 `@Pattern`，非法值直接抛 `IllegalArgumentException`。

**决策**：

1. 新增 `common/enums/EnumValueParser` 静态工具，签名 `parse(Class<E>, String raw, String fieldLabel)`。
2. 捕获 `IllegalArgumentException` 后抛 `BusinessException(40000, fieldLabel + "不合法: " + raw)`。
3. 上述 8 处全部改用统一解析。
4. 不做大小写之外的宽松匹配（保持现有 `trim().toUpperCase()` 行为）。
5. 非目标：`AdminAuditLogQueryService`（`#L134-L154`）与 `BehaviorEventType.parseOrNull` 已有 try/catch 兜底，不改。

**验收**：

- 非法 `status` 返回 `400`，错误文案包含字段名与非法值。
- 合法值与大小写混写行为不变。

### FR-11 全局异常脱敏（D6）

**现象**：兜底异常处理把 `ex.getMessage()` 直接返回前端，可能暴露 SQL、表名、内部类名。

**证据**：`common/exception/GlobalExceptionHandler.java#L62-L66`。

**决策**：

1. `handleOther` 响应固定为 `50000` +「系统繁忙，请稍后重试」。
2. 完整堆栈写 `ERROR` 日志，保留排查能力。
3. 业务异常、参数校验、权限异常的现有文案不变。

**验收**：

- 人为制造未捕获异常，响应中不含异常类名、SQL 或表名。
- 服务端日志仍能定位原始异常。

### FR-12 考试超时自动交卷（D7）

**现象**：学生断线或关闭页面后，`IN_PROGRESS` 提交在截止时间之后仍保持进行中，不结算、不进待批改统计。

**证据**：`exam/service/ExamService.java#L450-L522` 只在请求进入时处理；全仓仅 `AuditLogRetentionJob` 有 `@Scheduled`；`ExamSubmission` 已有 `deadlineAt`（`exam/entity/ExamSubmission.java#L21-L34`）。

**决策**：

1. 新增 `ExamAutoSubmitJob`，`@Scheduled(fixedDelay = 60000)`，每批最多处理 100 条；`@EnableScheduling` 已由 `common/audit/AuditLogConfig` 提供，不重复添加。
2. 扫描条件：`status = 'IN_PROGRESS'` 且 `deadline_at + 120s <= now`。120 秒是现有手动交卷的宽限期（`ExamService.java#L559`），抽为常量 `SUBMIT_GRACE_SECONDS`，手动交卷与定时任务共用，保证截止后 2 分钟内学生仍可自行提交。
3. 每条提交在 `REQUIRES_NEW` 独立事务中处理，单条失败不影响其他记录。
4. 抽取现有交卷逻辑为 `finalizeExamSubmission(submission, autoSubmit)`，学生手动交卷与定时任务共用，避免两套评分逻辑：
   - 手动交卷：沿用现有请求体中的答案，先落库再结算。
   - 自动交卷：不接收请求体，直接以已持久化的 `ExamAnswer` 草稿答案为结算依据；未作答题目按现有“未答即 0 分”规则处理。
5. 自动交卷后状态按现有规则置为 `AUTO_SUBMITTED` 或 `GRADED`（全客观题）。
6. 已结算记录由行锁 + 状态复查跳过；不发送通知。
7. 新建 `exam/service/ExamAutoSubmitJob`，用 `@ConditionalOnProperty(name = "app.exam.auto-submit.enabled", havingValue = "true", matchIfMissing = true)` 控制；`backend/src/test/resources/application-test.yml`（单测内存库）显式设为 `false`，避免定时任务改动 `ExamServiceTests` 的 `IN_PROGRESS` 夹具；主 `application-test.yml`（路径 B 开发库）保持默认开启。

**验收**：

- 截止后 2–3 分钟内（宽限期结束后的首个调度周期），超时 `IN_PROGRESS` 提交自动结算。
- 待批改统计与成绩记录同步出现。
- 多条超时记录中一条失败不影响其他记录。
- 手动交卷路径不回归。

## 8. 风险

| 风险 | 应对 |
|---|---|
| 跨校同名登录需前端增加学校编码，可能影响现有登录习惯 | 仅多条匹配时要求填写；单校用户无感 |

| 实验查重增加提交耗时 | 仅比较同一实验；异常降级为 0，不阻断提交 |
| 自动交卷任务与手动交卷并发 | 行锁 + 状态复查；独立事务隔离失败 |
| 密码编码切换导致历史账号无法登录 | Delegating + 无前缀兼容 + 登录后自动升级；发布前用演示账号验证 |
| 客观题禁改分可能被教师视为能力缺失 | 明确“客观题自动评分、主观题人工评分”的产品口径 |
