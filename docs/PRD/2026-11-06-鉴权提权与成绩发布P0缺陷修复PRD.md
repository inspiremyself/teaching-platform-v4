### 1.1 已定决策清单

| 编号 | 决策点 | 唯一结论 |
|---|---|---|
| D1 | 鉴权身份真相源 | 角色、学校、显示名、账号状态一律以数据库 `sys_user` 为准；JWT 声明不再作为授权依据 |
| D2 | Token 载荷收敛 | 新签发 token 仅保留 `sub`（用户名）、`uid`、`sid`、`iat`、`exp`；删除 `role`、`schoolId`、`displayName` 声明 |
| D3 | 旧 Token 兼容 | 过滤链忽略旧 token 中多余的 `role` / `schoolId` / `displayName`；密钥不变时不强制用户重新登录 |
| D4 | JWT 密钥配置 | `application.yml` 不再提供可用默认密钥；`local` / `test` profile 提供仅限本地开发的默认值；生产必须通过 `JWT_SECRET` 注入 |
| D5 | 密钥启动校验 | 启动时校验 `app.jwt-secret` 非空且 UTF-8 字节长度不少于 32，不满足直接启动失败并输出明确错误 |
| D6 | 密钥轮换影响 | 轮换 `JWT_SECRET` 会使全部存量 token 失效，所有用户需重新登录；本期不引入双密钥灰度 |
| D7 | 角色/学校变更生效时机 | 管理员修改角色、学校或状态后，在下一次请求即生效；本期不强制踢下线，列入后续迭代 |
| D8 | 实验提交状态机 | 仅 `SAVED` 状态的实验提交允许调用正式提交；`SUBMITTED` / `GRADED` 一律拒绝 |
| D9 | 已提交/已评分修改入口 | 学生不得自助重交；需要修改时由教师通过现有 `POST /teacher/lab-reports/{id}/return` 打回至 `SAVED` |
| D10 | 提交错误口径 | `SUBMITTED` 返回 `40000`「实验已提交，不能重复提交」；`GRADED` 返回 `40000`「实验已批改，如需修改请联系教师打回」 |
| D11 | 并发提交幂等 | 提交事务对当前学生的提交行加悲观写锁；并发重复提交只允许一次成功，另一次按状态被拒绝 |
| D12 | 成绩可见性真相源 | 学生成绩是否可见只由所属业务（考试/作业/实验）的可见性模式与提交状态决定；`score_record` 存在与否不代表可发布 |
| D13 | 各域可见性语义 | 沿用三域现有判定：`IMMEDIATE` 下考试/作业可见、实验要求 `totalScore != null`；未配置模式时默认 `AFTER_TEACHER_CONFIRM` |
| D14 | 学生成绩读取范围 | 所有学生端成绩读取必须过滤不可见成绩：`/analysis/my-scores`、`/analysis/my-score-overview`、`/analysis/student-dashboard`；返回结构不变 |
| D15 | 概览计算口径 | 平均分、最高分、已完成数、按业务分组、最近成绩反馈均只基于过滤后的可见成绩计算，禁止继续直接聚合裸 `score_record` 表 |
| D16 | 历史数据处理 | 本期不做批量删除、回填或改写；发布动作只改业务表 `score_released`，读取侧即时生效；教师打回已评分实验时删除对应 `score_record` 的既有行为保持不变 |
| D17 | 数据库变更 | 本期不新增 Flyway 迁移、不修改表结构 |
| D18 | 详情页判定复用 | 考试/作业/实验详情页现有判定保持不变；新增解析器放在 `analysis` 包内，用 `JdbcTemplate` 批量只读查询，禁止依赖 exam/homework/lab 的 Service，必须与详情页逐条对齐并用测试锁定 |
| D19 | 前端改动边界 | 学生实验页仅收敛“提交”按钮可用状态；登录页、成绩页、请求封装不改协议与字段 |
| D20 | 非目标 | 密码 BCrypt 迁移、`h2-console` 暴露、课程资料跨校隔离、作业时间窗、考试自动交卷均不在本期 |
| D21 | 业务缺失处理 | 成绩对应业务或提交记录不存在时直接剔除；删除现有 `lookupBusinessName` 的“未知”占位语义 |
| D22 | CurrentUser 字段来源 | `username`、`displayName`、`role`、`schoolId` 全部取自数据库实体；token 仅提供 `uid` 与 `sid`，`sub` 仅用于日志追踪，不参与身份构造 |
| D23 | 测试配置联动 | `backend/src/main/resources/application-test.yml` 与 `backend/src/test/resources/application-test.yml` 均需写入不少于 32 字节的测试密钥；`JwtAuthenticationFilterTests` 按数据库驱动重写 |

## 2. 背景与问题定位

### 2.1 背景

全项目自查中，前端 `vue-tsc` 与后端编译均通过、后端 44 个测试类全部通过。以下三项属于测试未覆盖、但一旦上线即造成提权、数据丢失或成绩泄露的高危缺陷，统一列为 P0。

### 2.2 根因

| 编号 | 现象 | 根因 |
|---|---|---|
| P1 | 教师可把自己的 token 改成校管角色，调用全部校管接口 | `JwtAuthenticationFilter` 直接使用 token 中的 `role` 与 `schoolId`，数据库只校验用户是否 `ACTIVE`，不比对真实角色；`application.yml` 与 `docker-compose.yml` 同时提供仓库内可见的默认密钥 |
| P2 | 实验已评分后学生再次提交，手工分与总分被清空 | `LabService.submitLab` 不校验当前提交状态，直接把状态置为 `SUBMITTED`；自动评分结果回填时把非自动评分的题分置为 `null`。保存与上传入口已有状态拦截，唯独正式提交入口缺失 |
| P3 | 教师未发布成绩，学生已在成绩页或工作台看到分数 | 考试、作业、实验批改时无条件写入 `score_record`；学生成绩列表、概览、工作台平均分与最近反馈均直接读取该表，完全不判断业务表的 `score_visibility_mode` 与 `score_released` |

### 2.3 代码证据

| 编号 | 证据 |
|---|---|
| P1 | `backend/.../auth/security/JwtAuthenticationFilter.java:58`、`:74-79`、`:100-107`；`backend/.../auth/security/JwtTokenService.java:35-48`；`backend/src/main/resources/application.yml:36`；`docker-compose.yml:26` |
| P2 | `backend/.../lab/service/LabService.java:1162-1188`、`:1750-1759`；对照 `ensureEditableSubmission` `:1378-1393` 已有状态拦截；教师打回入口 `:1293` |
| P3 | 写入侧 `backend/.../exam/service/ExamService.java:941-943`、`backend/.../lab/service/LabService.java:1729`、`backend/.../homework/service/HomeworkService.java:434-443`；读取侧 `backend/.../analysis/service/AnalysisService.java:151-163`（列表）、`:166-211`（概览，含 `:198-211` 分组聚合）、`:268-272`（工作台平均分）、`:466-479`（工作台最近反馈） |

### 2.4 影响面

- P1：任一教师账号在默认配置部署中可提权为校管，跨学校读写组织数据，属于最高级别越权。
- P2：已完成的教师评分被学生一次重交抹掉，且旧 `score_record` 仍保留，形成成绩数据不一致。
- P3：`MANUAL_RELEASE` 与 `AFTER_TEACHER_CONFIRM` 两种发布策略失效，未确认成绩提前泄露，直接影响教学公平与成绩发布流程。

## 3. 目标与成功标准

### 3.1 目标

1. 鉴权身份完全以数据库为准，token 篡改角色或学校不再产生任何权限效果。
2. 生产环境不存在可用的默认 JWT 密钥，缺失或过短时启动即失败。
3. 实验提交具备明确状态机，已提交/已评分记录只能由教师打回后修改。
4. 学生端所有成绩读取面（列表、概览、工作台）严格遵守各业务的成绩发布策略。

### 3.2 成功标准

- 用教师 token 篡改 `role=SCHOOL_ADMIN` 重签后调用校管接口，返回 403。
- 生产配置未注入 `JWT_SECRET` 时后端启动失败，错误信息包含 `app.jwt-secret`；注入 32 字节以上密钥后正常启动。
- 学生在实验 `GRADED` 后直接调用提交接口返回 400，分数、评语、总分、成绩记录均不变。
- 教师打回后学生可再次提交，提交链路与现有打回后行为一致。
- `MANUAL_RELEASE` 的考试/作业/实验在未发布前不出现在学生成绩列表、概览、工作台平均分与最近反馈；发布后无需数据修复即出现。
- `AFTER_TEACHER_CONFIRM` 下仅 `GRADED` 记录可见，`SUBMITTED` / `SAVED` 不可见。
- 学生只能看到自己的成绩，接口响应字段结构不变。

## 7. 核心流程

### 7.1 请求鉴权

1. 解析 Bearer token，取得 `uid` 与 `sid`。
2. 按 `uid` 查询 `sys_user`；用户不存在或状态非 `ACTIVE` 返回 401。
3. 按 `sid` 校验登录会话归属、状态与过期时间。
4. 用数据库用户的角色、学校、显示名构造 `CurrentUser`，不读取 token 中的角色与学校声明。
5. 后续 `@PreAuthorize` 与方法级归属校验照常执行。

### 7.2 实验正式提交

1. 校验学生身份、实验可访问、实验未关闭。
2. 加锁读取当前学生的实验提交；不存在返回「请先保存实验答案」。
3. 状态非 `SAVED` 时按 D10 拒绝，不产生任何写入。
4. 校验实验小结必填规则。
5. 置为 `SUBMITTED`、写入提交时间、逐题自动评分、刷新总分与状态、计算行为指标。

### 7.3 学生端成绩读取

1. 按当前学生查询全部 `score_record`。
2. 按业务类型分组，批量读取考试、作业、实验及其提交状态。
3. 逐条应用可见性规则；业务不存在、提交不存在或成绩为 `null` 的记录不返回。
4. 列表、概览、工作台统一复用同一份过滤结果：概览计算平均分、最高分、完成数与分组统计；工作台计算平均分、最近反馈与“我的成绩”角标。
5. 禁止任何学生端接口绕过解析器直接查询 `score_record` 聚合值。

## 8. 功能需求

### FR-1 鉴权身份以数据库为准

#### 8.1.1 Token 合约

- 新 token 载荷仅包含：`sub`（用户名）、`uid`、`sid`、`iat`、`exp`。
- 删除 `role`、`schoolId`、`displayName` 声明。
- 旧 token 中的多余声明允许存在但不读取，避免升级瞬间全员掉线。

#### 8.1.2 过滤链

- `JwtAuthenticationFilter` 只从 claims 读取 `uid`、`sid`、`sub`。
- 用户查询与状态校验合并为一次数据库读取，并复用该实体提供 `username`、`displayName`、`role`、`schoolId`；不再读取 token 中的用户名/显示名声明作为身份字段。
- 用户不存在、状态非 `ACTIVE`、会话无效、会话过期，统一返回现有 401 口径。
- 角色权限仍由 `ROLE_{role}` 注入安全上下文，来源为数据库角色。

#### 8.1.3 密钥配置与校验

- `application.yml` 改为 `jwt-secret: ${JWT_SECRET:}`，不提供可用默认值。
- `backend/src/main/resources/application-local.yml`、`backend/src/main/resources/application-test.yml`、`backend/src/test/resources/application-test.yml` 提供不少于 32 字节的本地/测试专用密钥，保证本地启动与 `./mvnw test` 可运行。
- `docker-compose.yml` 改为强制要求环境变量，例如 `${JWT_SECRET:?JWT_SECRET is required}`。
- `JwtTokenService` 构造时校验：非空且 UTF-8 字节长度不少于 32；不满足抛出启动异常，错误信息包含 `app.jwt-secret`。

#### 8.1.4 生效时机与轮换

- 角色、学校、状态修改在下一次请求生效，无需重新登录。
- 本期不因角色变更主动失效会话。
- 轮换密钥后全部存量 token 失效，用户重新登录；运维文档需注明该影响。

#### 8.1.5 验收标准

- 教师 DB 角色为 `TEACHER`，使用 `role=SCHOOL_ADMIN` 的旧 token 调用校管接口返回 403。
- 教师正常 token 调用教师接口返回 200。
- 停用用户即使持有未过期 token 也返回 401。
- 缺失 `JWT_SECRET` 且无 profile 默认值时启动失败；本地 profile 正常启动。
- 少于 32 字节的密钥启动失败。
- 登录、刷新用户信息、登出链路行为不变。

### FR-2 实验提交状态机

#### 8.2.1 状态规则

| 当前状态 | 提交行为 |
|---|---|
| 无提交记录 | `40000`「请先保存实验答案」 |
| `SAVED` | 允许提交 |
| `SUBMITTED` | `40000`「实验已提交，不能重复提交」 |
| `GRADED` | `40000`「实验已批改，如需修改请联系教师打回」 |

- 状态校验必须发生在置状态、写提交时间、自动评分、刷新总分、写行为指标之前。
- 拒绝时答案表、提交表、成绩表均无变化。
- `saveAnswer` / `uploadAnswerImage` 维持现有拦截，不重复改动。

#### 8.2.2 并发保护

- 提交事务按 `labId + studentId` 加悲观写锁读取提交行。
- 两个并发提交请求中，后进入者读取到 `SUBMITTED` 后按 D10 拒绝。
- 本期不新增唯一约束或迁移，复用行锁实现。

#### 8.2.3 前端行为

- 学生实验页仅当提交状态为 `SAVED` 时允许点击“提交实验”。
- 已提交或已评分时按钮禁用，并展示与后端一致的提示文案。
- 后端返回 400 时沿用现有错误提示，不清空本地作答展示。

#### 8.2.4 验收标准

- `SAVED` 提交成功，状态变为 `SUBMITTED`，自动评分与总分刷新正常。
- `SUBMITTED` 再次提交返回 400，提交时间与答案不变。
- `GRADED` 再次提交返回 400，题分、教师评语、总分、`score_record` 均不变。
- 教师调用打回接口后，学生可再次提交并走完整评分链路。
- 并发两次提交只产生一次状态推进。

### FR-3 学生成绩发布可见性

#### 8.3.1 真相源与前置条件

- 可见性只由业务表与提交表决定，`score_record` 仅作为成绩数值载体。
- 前置条件：业务记录存在且状态不为 `DRAFT`，当前学生存在对应提交，成绩值非 `null`。
- 前置条件不满足时该条成绩不返回。
- `score_released` 在数据库为非空布尔，不存在空值分支。
- 业务不存在时不得返回 `businessName = "未知"` 的占位记录；工作台最近反馈同样剔除。

#### 8.3.2 可见性矩阵

| 模式 | 考试 | 作业 | 实验 |
|---|---|---|---|
| `IMMEDIATE` | `true`（受 §8.3.1 前置条件约束） | `true`（受 §8.3.1 前置条件约束） | `submission.totalScore != null` |
| `AFTER_TEACHER_CONFIRM` | `submission.status = GRADED` | `submission.status = GRADED` | `submission.status = GRADED` |
| `AFTER_DEADLINE` | `exam.endAt != null && now >= endAt` | `homework.dueAt != null && now >= dueAt` | `lab.endAt != null && now >= endAt` |
| `MANUAL_RELEASE` | `exam.scoreReleased` | `homework.scoreReleased` | `lab.scoreReleased` |

- 模式为空时按 `AFTER_TEACHER_CONFIRM` 处理。
- 矩阵必须与各详情页现有判定一致：`ExamService.canStudentSeeScore`、`HomeworkService.isStudentScoreVisible`、`LabService.scoreVisible`。
- 数值 0 分必须正常可见，禁止用真假值判断分数是否存在。

#### 8.3.3 接口范围

- `GET /api/v1/analysis/my-scores`：返回过滤后的列表，字段结构不变。
- `GET /api/v1/analysis/my-score-overview`：`averageScore`、`highestScore`、`completedItems`、`completionRate`、`groupedScores`、`recentRecords`、`feedbackNotes` 全部基于过滤后的列表计算，不再直接聚合裸表。
- `groupedScores` 保持按 `business_type` 升序；无可见记录时 `averageScore`、`highestScore`、`completionRate` 返回 `0.0`，`completedItems` 返回 `0`。
- `GET /api/v1/analysis/student-dashboard`：`summaryCards.averageScore`、`recentFeedback` 基于过滤后的列表计算；“我的成绩”角标沿用现状取过滤后最近反馈条数（最多 4）；资料相关字段不在本期。
- 教师端成绩分析、校管端统计不受影响。

#### 8.3.4 性能要求

- 单次成绩列表、概览、工作台查询的 SQL 数量固定，不随成绩条数增长。
- 禁止逐条查询业务表与提交表造成 N+1。

#### 8.3.5 验收标准

- `MANUAL_RELEASE` 考试已批改未发布：列表、概览、工作台平均分与最近反馈均不含该成绩；调用发布接口后立即出现，无需改数据。
- 作业、实验同样通过。
- `AFTER_TEACHER_CONFIRM`：`SUBMITTED` 不可见，`GRADED` 可见。
- `AFTER_DEADLINE`：截止前不可见，截止后可见。
- `IMMEDIATE`：行为与改造前一致。
- 0 分成绩可见。
- 业务缺失记录不出现“未知”占位，直接不返回。
- 学生 A 不返回学生 B 的任何成绩。
- 返回字段与改造前一致，前端无需改解析逻辑。

## 14. 风险与回滚

| 风险 | 影响 | 应对 |
|---|---|---|
| 生产未配置 `JWT_SECRET` | 后端无法启动 | 发布前在部署清单中强制检查；Docker Compose 使用必填变量 |
| 轮换密钥 | 全部用户被迫重新登录 | 选择低峰期执行，并提前公告 |
| 外部客户端解析 token 声明 | 依赖 `role` 的客户端失效 | 前端已确认不解析 token；对外接口以 `/auth/me` 为准 |
| 列表过滤与详情页判定漂移 | 同一成绩两处展示不一致 | 解析器与三域现有判定逐条对齐，增加一致性测试 |
| 工作台成绩漏改 | 学生仍能从工作台看到未发布成绩 | 学生端 `score_record` 查询统一走解析器，测试覆盖 `student-dashboard` |
| 路径 A 一键启动失败 | Docker Compose 缺少 `JWT_SECRET` 无法启动 | `scripts/path-a/up.sh` 自动生成并注入本地开发密钥 |
| 并发锁引入等待 | 极端并发下提交变慢 | 锁粒度限定为单学生单实验提交行 |

回滚策略：代码回滚至上一版本即可恢复；若仅密钥配置导致问题，优先修正环境变量而不是回退代码。已发布成绩的 `score_released` 为业务数据，回滚代码不会自动回收，需人工确认。
