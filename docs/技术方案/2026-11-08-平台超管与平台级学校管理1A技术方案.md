## 3. 后端实现规格

### 3.1 `V25__platform_admin_role.sql`

文件含且仅含以下两条 SQL（V1.3 修订：主键由 `MAX(id)+1` 显式分配，**不写死 `id=6`**，也不依赖 `AUTO_INCREMENT` 计数器）：

```sql
ALTER TABLE sys_user ${alterModifyColumn} school_id BIGINT NULL;

INSERT INTO sys_user (id, username, password_hash, role, display_name, status, must_change_password, school_id, last_login_at, created_at, updated_at)
SELECT COALESCE(MAX(id), 0) + 1,
       'platform9001', '{noop}123456', 'PLATFORM_ADMIN', '演示平台超管', 'ACTIVE', FALSE,
       NULL, NULL, CURRENT_TIMESTAMP, CURRENT_TIMESTAMP
FROM sys_user;
```

- 第 1 条与 `V18` 第 1 行同形态，`${alterModifyColumn}` 由 `FlywayPlaceholdersConfig` 按 DataSource 注入（MySQL `MODIFY COLUMN` / H2 `ALTER COLUMN`），四个 `application*.yml` 不新增占位符声明。
- 第 2 条按 `V13` 第 50–54 行的显式列清单；口令写 `'{noop}123456'`（沿用 Flyway 种子形态），首次登录由 `AuthService.needsUpgrade` 升级为 `{bcrypt}`；`role='PLATFORM_ADMIN'` 长度 14 ≤ `V1` 的 `VARCHAR(16)`；`last_login_at` 与 `school_id` 均为 NULL。
- 三角色历史行取值不变；`uk_sys_user_school_username(school_id, username)` 保持原样，不加部分索引 / 生成列 / DB CHECK；NULL 不参与唯一约束，账号唯一由「仅此一条种子 + 不提供新增接口」保证。
- `SCHEMA.md` 同步范围**仅限 `sys_user` 一节**：现网该文件第 16–37 行未列 `school_id`、唯一约束仍写 `UNIQUE (username)`（V13 之后的历史漂移）。1A 只在该节补一行 `| school_id | BIGINT | 是 |  | NULL 仅表示平台级账号（无学校归属），不代表任何学校；其余为所属学校 id |`（V1.4 按总纲 §5 补齐 NULL 语义），并把该节唯一约束更正为 `UNIQUE (school_id, username)`；**不触碰其它表节**，其余历史漂移登记为独立运维事项、不并入 1A。总纲 §4 / §5 的「随当期迁移同步」按此最小范围落地。

**口径裁决（写死）**：`backend-db-and-config.mdc` §2.2 / §5 禁止「新迁移里塞演示账号」，与总纲 D16、PRD FR-1 要求的 `V25` 种子 INSERT 冲突。按 `code-conventions.mdc` §1.4 优先级（现网 `db/migration/` 行为 > 已定稿技术方案）与 `V2` / `V13` 既有 Flyway 种子账号先例，本方案按 PRD 执行：`V25` 只写 1 条系统基线账号，不写任何演示业务数据、不做覆盖 / 清除本地业务数据的 DML，且 `DemoAccountProdGuard` 在 prod 禁用该账号。编码阶段不得在此二选一；若后续规则收紧，须另起方案修订，不在 1A 内自行改道。

### 3.2 实体与枚举

| 文件 | 改动 |
|---|---|
| `auth/UserRole.java` | 枚举末尾追加 `PLATFORM_ADMIN`（顺序固定为 `SCHOOL_ADMIN, TEACHER, STUDENT, PLATFORM_ADMIN`），不改动前三值 |
| `auth/entity/SysUser.java` | 第 22 行 `@Column(name = "school_id", nullable = false)` → `nullable = true`；其余列、getter / setter 一字不改 |
| `common/infra/audit/AuditAction.java` | 在 `SCHOOL_UPDATE` 之后追加 `SCHOOL_CREATE`、`SCHOOL_STATUS`；不删除已有值 |
| `material/service/MaterialService.java` | `listMaterials` 的 `switch (currentUser.role())` 是**无 default 的穷尽 switch 表达式**，新增枚举值后不补 case 会直接编译失败。追加唯一分支 `case PLATFORM_ADMIN -> throw new BusinessException(40300, "无权限访问资料");`（仅用于编译穷尽与运行时兜底，`MaterialController` 第 32 / 61 行的 `hasAnyRole('TEACHER','STUDENT','SCHOOL_ADMIN')` 本就拦截平台超管）；`uploadMaterial` 等其它方法与三角色分支一字不改 |

`SchoolStatus`、`UserStatus` 不变。`CurrentUser` 仍为 6 组件 record，便捷构造 `schoolId=1L` 仅供三角色测试。全仓 `UserRole` 相关 switch 共 3 处：`AuthService.permissionsOf`（无 default 表达式，§3.3 补 case）、`MaterialService.listMaterials`（无 default 表达式，本表补 case）、`PlagiarismService.getTaskDetail`（switch **语句**且已有 `default -> 40300`，**不改**，平台超管自然走 default 拒绝）；其余 switch 均为题型 / 状态等非 `UserRole` 枚举，不受影响。

### 3.3 `AuthService` 三处改动（写死到方法粒度）

1. **`permissionsOf(SysUser)`**：switch 表达式追加 `case PLATFORM_ADMIN -> List.of("SCHOOL_READ", "SCHOOL_WRITE", "SCHOOL_PROVISION");`；三角色分支与顺序一字不改。登录响应 `permissions` 由该方法产出，不另建映射。
2. **`toUserProfile(SysUser user)`**：保持单参、两个调用点（`getCurrentUserProfile` / `updateProfile`）不改。方法体内 `profile.put("schoolId", ...)` 与 `schoolRepository.findById(...)` 一并包进 `if (user.getSchoolId() != null)`；为 null 时两个键都不写，其余键（`id` / `username` / `displayName` / `role` / `email` / `phone` / `officeHours` / `bio` / `mustChangePassword` / `permissions`）顺序与取值不变。禁止对 null 调用 `findById`。
3. **`login(LoginRequest)`**：在现有 `user.getStatus() != UserStatus.ACTIVE` 分支之后、`matchesPassword` 之前插入唯一一段：

```java
if (user.getSchoolId() != null) {
    School school = schoolRepository.findById(user.getSchoolId()).orElse(null);
    if (school == null || school.getStatus() == SchoolStatus.DISABLED) {
        logLoginFailure(user.getId(), user.getSchoolId(), request);
        throw new BusinessException(LOGIN_DISABLED_CODE, LOGIN_DISABLED_MESSAGE);
    }
}
```

- `schoolId == null`（平台超管）直接跳过，不查库、不抛 `findById(null)`。
- `40103` 与现网 `LOGIN_DISABLED_MESSAGE`「该账号已被停用，请联系管理员」复用，不改文案、不新增错误码；学校记录缺失与 `DISABLED` 同分支，不单独暴露学校存在性。
- `findAllByUsernameAndRole`、`schoolCode` 消歧、会话处理、JWT 签发、登录成功审计（`SecurityAuditEvent` 取 `saved.getSchoolId()`）顺序全部不动。
- 三角色登录成功 / 失败审计沿用现网 `user.getSchoolId()` 取值；FR-4 的「写 NULL」口径只适用于平台超管。

### 3.4 `DemoAccountProdGuard`

`SQL` 常量改为唯一形态：

```java
private static final String SQL = "UPDATE sys_user SET status = 'DISABLED' "
        + "WHERE (school_id = 1 OR school_id IS NULL) AND status = 'ACTIVE' "
        + "AND username IN ('t9001','20260001','20260002','admin9001','t9002','platform9001')";
```

保留 `school_id = 1` 条件（避免误禁用其它学校同名账号），必须带 `school_id IS NULL` 分支（否则 NULL 行不被覆盖）。类注解、`@Profile("prod")`、`run` 逻辑不变。

|---|---|---|---|
| `GET` | `/api/v1/admin/schools` | 无 | `ApiResponse<List<PlatformSchoolItem>>` |
| `POST` | `/api/v1/admin/schools` | `@Valid @RequestBody CreateSchoolRequest` | `ApiResponse<PlatformSchoolItem>` |
| `POST` | `/api/v1/admin/schools/{schoolId}/status` | `@Valid @RequestBody UpdateSchoolStatusRequest` + `@PathVariable Long schoolId` | `ApiResponse<PlatformSchoolItem>` |

Controller 只取参、转发 service，不写业务判断；`CurrentUser` 由 `SecurityUtils.currentUser()` 在 service 层取（service 方法签名接收 `CurrentUser`）。**不加类级 `@Validated`**：`@PathVariable Long schoolId` 无约束注解，类级 `@Validated` 只用于 `@RequestParam` / `@PathVariable` 约束场景（`backend-code-style.mdc` §3.4）；请求体校验由 `@Valid @RequestBody` 触发，`schoolId` 为 0 / 负数时走 `findById` 空值 → `40400`，不新增参数错误码。

**Service**（新建 `admin/service/PlatformSchoolService.java`，显式 public 构造器注入 `SchoolRepository` / `SysUserRepository` / `PasswordEncoder` / `AuditLogService`）：

- `listSchools()`：`schoolRepository.findAll(Sort.by(Sort.Direction.ASC, "id"))`；按校取 `sysUserRepository.findBySchoolIdAndRole(schoolId, UserRole.SCHOOL_ADMIN)`，`stream().min(Comparator.comparing(SysUser::getId)).map(SysUser::getUsername).orElse("")`；不新增 Repository 方法。
- `createSchool(CurrentUser, CreateSchoolRequest)`：`@Transactional`。方法入口先写死三个归一化局部变量：`String name = request.name().trim(); String code = request.code().trim(); String adminUsername = request.adminUsername().trim();`，**校验、入库、审计、返回一律只用这三个局部变量**，`adminPassword` 原样使用、不 trim。① `schoolRepository.findByCode(code).isPresent()` → `BusinessException(40904, "学校编码已存在")`；② `new School()` 设 `name` / `code` / `SchoolStatus.ACTIVE`，`saveAndFlush` 取 id；③ `sysUserRepository.existsBySchoolIdAndUsername(saved.getId(), adminUsername)` → `BusinessException(40905, "该校已存在同名账号")`；④ `new SysUser()` 设 `schoolId=saved.getId()`、`username=adminUsername`、`passwordHash=passwordEncoder.encode(request.adminPassword())`、`role=SCHOOL_ADMIN`、`displayName=adminUsername`（1A 表单不收集姓名，用账号名作显示名，避免多校都显示「校管」）、`status=UserStatus.ACTIVE`、`mustChangePassword=false`，`save`；⑤ `auditLogService.log(currentUser, AuditAction.SCHOOL_CREATE, AuditResourceType.SCHOOL, saved.getId(), Map.of("targetSchoolId", saved.getId(), "code", saved.getCode(), "adminUsername", adminUsername))`；⑥ 返回 `toItem(saved, adminUsername)`。任一步抛异常整体回滚。跨校同名账号不在 1A 禁止范围，由登录 `schoolCode` 消歧。若不归一化，带前后空格的 `code` 会绕过 `findByCode` 校验并最终撞 `school.code UNIQUE` 返回 500，属明确禁止的实现路径。
- `updateSchoolStatus(CurrentUser, Long schoolId, UpdateSchoolStatusRequest)`：`@Transactional`。① `schoolId == 1L && request.status() == SchoolStatus.DISABLED` → `BusinessException(40028, "演示学校不可停用")`；② `schoolRepository.findById(schoolId).orElseThrow(() -> new BusinessException(40400, "学校不存在"))`；③ `school.setStatus(request.status())` + `save`；④ `auditLogService.log(currentUser, AuditAction.SCHOOL_STATUS, AuditResourceType.SCHOOL, schoolId, Map.of("targetSchoolId", schoolId, "status", request.status().name()))`；⑤ 返回 `toItem(...)`（`adminUsername` 走与列表相同的最小 id 取值）。不删用户、不改 `user_login_session`。
- `Map.of` 所有值非 null；不引入 `Map` 之外的新 detail 结构。

**错误码**：`40028`（400 段）、`40904` / `40905`（409 段）、`40000` / `40001` 参数、`40400` 未找到、`40103` 复用；全部落在 `GlobalExceptionHandler` 既有段位，不改映射、不改前端 `SILENT_CODES` / `AUTH_FAILURE_CODES`。

### 3.6 明确不改项

`SecurityConfig`（仍只 permitAll `/api/v1/auth/login`）、`JwtAuthenticationFilter`（仍传 `user.getSchoolId()`）、`CurrentUser`（6 组件）、`SysUserRepository` / `SchoolRepository`（无新方法）、6 个 admin controller 与 service（类级注解与按校过滤）、`AuthController`、`HttpAccessLogFilter`（平台超管 `school_id` 自然为 NULL）、`user_login_session` 结构与会话逻辑：全部一字不改。

## 9. 风险与回滚

| 风险 | 应对 / 回滚 |
|---|---|
| `V25` 的 `ALTER` 在 H2 / MySQL 方言不兼容 | 与 `V18` 第 1 行同形态且 `${alterModifyColumn}` 由 `FlywayPlaceholdersConfig` 注入；三套数据库形态先跑 Flyway，失败即停，不进编码 |
| 放开 `NOT NULL` 后 NULL 不参与 `uk_sys_user_school_username`，同名超管被误插两条导致登录多账号错误 | 账号只由 `V25` 单条种子创建、1A 不提供新增接口；`PlatformAdminScopeTests` 断言唯一；登录 `findAllByUsernameAndRole` 应只返回 1 行 |
| `schoolRepository.findById(null)` 使平台超管无法登录 | §3.3 显式 `schoolId != null` 守卫 + `AuthServiceTests` 覆盖；回滚点为 `AuthService.login` 新增分支 |
| `layout/index.vue` 未同步改造导致平台超管看到学生侧栏 | §4.3 写死 `resolveRoleView` 六字段取值表，新建 `roleView.spec.ts` 覆盖；`guard.spec.ts` 覆盖 `resolveHomePath` / `shouldRedirectToHome`；PRD §3.2 手工验收逐条核对 |
| 停用学校校验误伤平台超管或改变三角色登录顺序 | 校验点固定在 `user.status` 之后、密码之前，仅对 `schoolId != null` 生效；三角色既有登录测试全量回归 |
| 备份缺失 | §6 步骤 2 为硬门禁，未备份不得写 `V25`；恢复用 `restore-local-data.sh --latest --with-files`（须先停后端） |
| 上线回滚 | `V25` 不删除数据、只放宽列约束与新增 1 行账号；回滚 = 停用 `platform9001` + 回退 1A 代码，`V1`–`V24` 与本地业务数据不受影响；禁止改已应用迁移 |
