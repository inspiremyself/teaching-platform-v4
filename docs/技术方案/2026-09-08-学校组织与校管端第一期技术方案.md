# 学校组织与校管端（第一期）技术方案

**创建日期**：2026-09-08  
**状态**：已定稿（决策写死，可直接编码）  
**范围**：单校场景下引入 `school` 组织层、`SCHOOL_ADMIN` 校管端（`/admin`），由校管统一维护本校教师、班级、学生及归属关系；收窄教师端组织管理能力

## 1. 背景与诉求

### 1.1 业务诉求

建立与真实教务组织一致的主线：

```text
学校
 ├── 教师（多名）
 ├── 学生（多名，每人归属唯一班级）
 └── 班级（多名，每班可绑定多名教师：班主任 + 学科教师）
      └── 学生名册
```

第一期由**学校管理员**统一维护组织关系；教师专注教学业务（资料、题库、实验、作业、考试、批改、分析），不再自建班、自建学生账号。

### 1.2 现状结论（调研）

| 能力 | 现状 | 缺口 |
|------|------|------|
| 学校实体 | 无 | 无组织顶层 |
| 用户归属 | `sys_user` 全局扁平账号 | 无 `school_id` |
| 角色 | 仅 `TEACHER` / `STUDENT` | 无校管 |
| 班级归属 | `class_room.teacher_user_id` 外键直挂 | 应拆为关系表；且无 `school_id` |
| 学生归属 | `class_member` 关联 | 可多班；教师可建/导入学生 |
| 教师端导航 | 「班级管理」「学生管理」与教学菜单并列 | 组织与教学边界模糊 |
| 管理端 | 无 | 需 `/admin` 壳层 |

### 1.3 设计结论（一句话）

**新增 `school`、`class_teacher` 与 `SCHOOL_ADMIN`，用 Flyway V13 补 `school_id`、迁移师生归属至关系表并删除 `class_room.teacher_user_id`；组织 CRUD 迁至 `/api/v1/admin/*` + `/admin` 前端。**

## 2. 目标与非目标

### 2.1 目标

1. 数据模型表达：**学校 → 教师/学生；班级 → 学生（唯一）；教师 ↔ 班级（多对多，含学科教师）**。
2. 校管可维护：学校信息、教师账号、班级（含指派多名教师及学科）、学生（含分班/调班/导入/启停）。
3. 教师端移除组织维护入口；班级下拉等只读能力保留。
4. 演示种子数据与路径 B 探活脚本在新增校管账号后仍可一键验收。
5. 全部组织写操作写审计日志（沿用 `AuditLogService`）。

### 2.2 非目标（第一期）

- 平台超管、多校列表、跨校切换、学校开通/停用流程。
- 院系、年级、专业、学籍异动审批流。
- 教师端保留「新建班级 / 新增学生 / 导入学生」任何入口。
- 学生/教师账号物理删除、批量导出、LDAP/SSO。
- 题库/资料/实验等业务表的 `school_id` 改造（仍按教师 `created_by` / 班级 `class_id` 间接归属）。
- 学生多班就读、走班制。
- 学科与课表系统对接（排课、课时）；`subjectName` 仅为组织层手工标注。

## 3. 数据模型

### 3.1 ER（第一期）

```text
school (1)
  │
  ├──1:N── sys_user
  │         role ∈ { SCHOOL_ADMIN, TEACHER, STUDENT }
  │         UNIQUE(school_id, username)
  │
  └──1:N── class_room
            school_id
            name / code / status
            UNIQUE(school_id, code)
            │
            ├──1:N── class_teacher          ← 教师↔班（多对多）
            │         teacher_user_id → sys_user(TEACHER)
            │         role ∈ { HEAD, SUBJECT }
            │         subject_name（SUBJECT 必填）
            │         UNIQUE(class_id, teacher_user_id)
            │         业务约束：每班 HEAD ≤ 1
            │
            └──1:N── class_member           ← 学生↔班
                      UNIQUE(student_user_id)    ← 一人一班
                      student_user_id → sys_user(STUDENT)
```

**对称设计**：`class_member` 管学生归属，`class_teacher` 管教师归属；`class_room` 只承载班级本体属性。

### 3.2 新表 `school`

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增 |
| `name` | VARCHAR(128) NOT NULL | 学校名称 |
| `code` | VARCHAR(64) NOT NULL UNIQUE | 学校编码（全局唯一，第一期仅一条） |
| `status` | VARCHAR(16) NOT NULL | `ACTIVE` / `DISABLED` |
| `created_at` / `updated_at` | TIMESTAMP | 审计字段 |

Java：`com.opencode.teachingplatform.school.entity.School`  
枚举：`SchoolStatus { ACTIVE, DISABLED }`

### 3.3 变更 `sys_user`

| 变更 | 说明 |
|------|------|
| 新增 `school_id BIGINT NOT NULL` | 所有角色必填 |
| 唯一约束 | 删除 `username` 单列唯一；新增 `UNIQUE(school_id, username)` |
| 角色 | `UserRole` 增加 `SCHOOL_ADMIN` |

### 3.4 变更 `class_room`

| 变更 | 说明 |
|------|------|
| 新增 `school_id BIGINT NOT NULL` | 班级归属学校 |
| 删除 `teacher_user_id` | 师生归属迁至 `class_teacher` |
| 唯一约束 | 删除 `code` 单列唯一；新增 `UNIQUE(school_id, code)` |

`ClassRoom` 实体删除 `teacherUserId` 字段；API 中教师指派信息以 **`teachers[]` 数组** 返回（见 §5.3），不再使用单个 `teacherUserId` / `teacherName` 字段。

### 3.5 新表 `class_teacher`

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增 |
| `class_id` | BIGINT NOT NULL | → `class_room.id` |
| `teacher_user_id` | BIGINT NOT NULL | → `sys_user.id`（`TEACHER`） |
| `role` | VARCHAR(16) NOT NULL | `HEAD`（班主任）或 `SUBJECT`（学科教师） |
| `subject_name` | VARCHAR(64) NULL | `role=SUBJECT` 时**必填**（trim 后 1～64 字符）；`HEAD` 必须为 `null` |
| `assigned_at` | TIMESTAMP NOT NULL | 指派时间 |
| `created_at` / `updated_at` | TIMESTAMP | 审计字段 |

约束（写死）：

- `UNIQUE(class_id, teacher_user_id)` — 同一教师不能重复加入同一班级
- **不设** `UNIQUE(class_id)` — 允许多名教师同属一班
- `HEAD` 每班最多 1 人：由 **Service 校验**（违反 → `40022`），不建 DB 部分唯一索引（H2/MySQL 兼容成本过高）

Java：

- `com.opencode.teachingplatform.clazz.entity.ClassTeacher`
- `com.opencode.teachingplatform.clazz.repository.ClassTeacherRepository`
- 枚举 `ClassTeacherRole { HEAD, SUBJECT }`（放 `common/enums`）

**角色语义**：

| role | 含义 | 数量 | subject_name |
|------|------|------|--------------|
| `HEAD` | 班主任 | 每班 0～1 | 必须为空 |
| `SUBJECT` | 学科教师 | 每班 0～N | 必填，如「软件体系结构」 |

**写入语义**：

- 校管创建班级：先 `INSERT class_room`，再批量 `INSERT class_teacher`（`teachers` 至少 1 条）。
- 校管更新班级教师：**全量快照替换** — `DELETE FROM class_teacher WHERE class_id = ?`，再按请求体 `teachers[]` 批量插入（同一事务）。
- 校管删除班级：班内有学生 → `40020`；否则删 `class_teacher` → 删 `class_room`。

**校验**：`teacher_user_id` 对应用户必须是本校 `TEACHER` 且 `ACTIVE`，且 `class_room.school_id` 与教师 `school_id` 一致。

### 3.6 变更 `class_member`

| 变更 | 说明 |
|------|------|
| 新增 `UNIQUE(student_user_id)` | 强制学生全局仅一条班级_membership（单校内即一班） |
| 保留 `UNIQUE(class_id, student_user_id)` | 与上条不冲突 |

**调班语义**：校管 `PUT /admin/students/{id}` 修改 `classId` 时，**更新既有 `class_member` 行的 `class_id`**，不新增第二行。

### 3.7 Flyway `V13__school_organization_phase1.sql`（写死顺序）

1. `CREATE TABLE school (...)`  
2. `INSERT INTO school (id, name, code, status, ...) VALUES (1, '演示学校', 'DEMO-SCHOOL', 'ACTIVE', ...)`  
3. `ALTER TABLE sys_user ADD COLUMN school_id BIGINT` → 回填 `1` → `NOT NULL`  
4. 删除 `sys_user` 上 `username` 唯一索引/约束 → 建 `uk_sys_user_school_username (school_id, username)`  
5. `ALTER TABLE class_room ADD COLUMN school_id BIGINT` → 回填 `1` → `NOT NULL`  
6. 删除 `class_room.code` 唯一 → 建 `uk_class_room_school_code (school_id, code)`  
7. `CREATE TABLE class_teacher (...)`  
8. `INSERT INTO class_teacher (class_id, teacher_user_id, role, subject_name, assigned_at, ...)`  
   `SELECT id, teacher_user_id, 'SUBJECT', '未标注学科', NOW(), ... FROM class_room WHERE teacher_user_id IS NOT NULL`  
9. `ALTER TABLE class_room DROP COLUMN teacher_user_id`  
10. 清理 `class_member` 重复 `student_user_id`（种子无重复）  
11. 建 `uk_class_member_student (student_user_id)`  
12. `INSERT INTO sys_user` 校管 `admin9001`（`school_id=1`, `role=SCHOOL_ADMIN`）  
13. 演示补强：新增教师 `t9002`（`李老师`）+ `class_teacher(class_id=1, role=SUBJECT, subject_name='数据库原理')`；`UPDATE` 将 `t9001` 对应行 `subject_name='软件体系结构'`  
14. 现有 `t9001`、`20260001` 保持 `school_id=1`（步骤 3 已回填）

H2 / MySQL 兼容：用 Flyway 惯用 `ALTER`；若索引名冲突，迁移内显式 `DROP INDEX` 再创建。

## 4. 鉴权与数据范围

### 4.1 角色权限矩阵

| 能力 | SCHOOL_ADMIN | TEACHER | STUDENT |
|------|:------------:|:-------:|:-------:|
| 维护学校信息 | ✅ 本校 | — | — |
| 教师 CRUD（启停） | ✅ 本校 | — | — |
| 班级 CRUD | ✅ 本校 | — | — |
| 学生 CRUD / 导入 / 调班 | ✅ 本校 | — | — |
| 班级只读列表 | ✅ 本校全校 | ✅ 仅 `class_teacher.teacher_user_id=自己` 的班 | — |
| 教学业务（实验/作业/考试等） | — | ✅ 已指派该班（`class_teacher` 含自己）即可操作 | ✅ 现有规则 |

### 4.2 校管数据范围（写死）

所有 `Admin*Service` 入口第一步：

```java
Long schoolId = currentUser.schoolId();
// 后续查询/写入均带 school_id = schoolId
```

校验规则：

- 创建/更新班级：`teachers[]` **全量快照**写入 `class_teacher`；至少 1 名教师；`HEAD` ≤ 1；`SUBJECT` 必填 `subjectName`；目标教师必须本校 `TEACHER` 且 `ACTIVE`。
- 创建/更新学生：`classId` 必须是本校班级；写入 `sys_user.school_id = schoolId`。
- 调班：目标班级必须本校；更新唯一 `class_member` 行。
- 校管**不能**通过 admin API 修改非本校用户。

### 4.3 教师数据范围与教学鉴权对齐

**班级只读（`ClassService`）**

- `listTeacherClasses` / `findOwnedClass` / `assertTeacherOwnsClass`：统一委托 **`ClassAccessService.assertTeacherAssignedToClass`**。
- `ClassRoomRepository.findByTeacherUserId` / `findByIdAndTeacherUserId` **删除**；按教师查班改由 `ClassTeacherRepository` + join `class_room`。

**`ClassAccessService`（新建，写死）**

```java
void assertTeacherAssignedToClass(CurrentUser currentUser, Long classId);
List<ClassRoom> listAssignedClasses(CurrentUser currentUser);
```

- 判定：`EXISTS class_teacher WHERE class_id=? AND teacher_user_id=当前用户` 且 `class_room.school_id=当前用户.schoolId`。
- 当前用户非 `ACTIVE` → 40300。

**教学业务改造范围（第一期必做）**

| 服务 | 改造点 |
|------|--------|
| `HomeworkService` | 创建/更新作业前 `assertTeacherAssignedToClass(classId)`；替换原 `findByIdAndTeacherUserId` |
| `LabService` | 创建/更新实验前同上；教师报告/批改入口同上 |
| `ExamService` | **`createExam` / `updateExam`（改 `classId`）** 前 `assertTeacherAssignedToClass(request.classId())`（现网 `createExam` 缺失）；批改/查看仍限 `created_by=自己` |
| `AnalysisService` | 原生 SQL 中 `cr.teacher_user_id` 改为 `JOIN class_teacher ct ON ct.class_id=cr.id AND ct.teacher_user_id=?` |
| `ClassService` | 只读 list/get 走 `ClassAccessService` |

**列表范围（写死，第一期不改）**

- 作业/实验/考试教师列表仍按 **`created_by = 当前用户`**（教师只看到自己创建的任务）。
- 同班多师可**各自发布**自己创建的任务；不要求互相看见或批改对方创建的任务（B5 验收口径）。

### 4.4 JWT 与 CurrentUser

`JwtTokenService.issueToken` 增加：

```java
.claim("schoolId", user.getSchoolId())
```

`CurrentUser` 变更为：

```java
public record CurrentUser(Long id, String username, String displayName, UserRole role, Long schoolId, String sessionKey) {
    public CurrentUser(Long id, String username, String displayName, UserRole role) {
        this(id, username, displayName, role, 1L, null);
    }
}
```

`JwtAuthenticationFilter` 从 claim 解析 `schoolId` 注入；session 校验通过后**读取 `loginSession.user.status`**，非 `ACTIVE` 返回 **40100**（实现 A8「停用后已有 token 失效」）。旧 token 无 `schoolId` claim 时同样返回 **40100**（开发环境重新登录）。

### 4.5 登录与 permissions

`AuthService.permissionsOf`（写死完整列表）：

- `SCHOOL_ADMIN` → `["SCHOOL_READ","SCHOOL_WRITE","TEACHER_READ","TEACHER_WRITE","CLASS_READ","CLASS_WRITE","STUDENT_READ","STUDENT_WRITE"]`
- `TEACHER` → `["CLASS_READ","LAB_WRITE","HOMEWORK_WRITE","EXAM_WRITE","ANALYSIS_READ"]`（**删除**现网 `CLASS_WRITE`）
- `STUDENT` → `["MATERIAL_READ","LAB_READ","HOMEWORK_READ","EXAM_READ","SCORE_READ"]`（不变）

`GET /api/v1/auth/me` 响应增加：

```json
{
  "schoolId": 1,
  "schoolName": "演示学校"
}
```

## 5. 后端 API 设计

统一前缀 `/api/v1/admin`，响应结构沿用 `ApiResponse` / `PagedResult`。

### 5.1 学校信息

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/admin/school` | 返回当前校管的学校信息 |
| PUT | `/admin/school` | 更新 `name`（`code` 第一期只读，不可改） |

**GET 响应字段**：`id`, `name`, `code`, `status`

**PUT 请求体**：`{ "name": "string" }`（`@NotBlank`，trim 后 1～128 字符）

### 5.2 教师管理

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/admin/teachers` | 本校教师列表；支持 `?status=ACTIVE` |
| POST | `/admin/teachers` | 创建教师 |
| PUT | `/admin/teachers/{id}` | 更新 `displayName` |
| POST | `/admin/teachers/{id}/status` | `{ "status": "ACTIVE" \| "DISABLED" }` |

**列表项字段**：`id`, `username`, `displayName`, `status`, `classCount`（`class_teacher` 关联且 `class_room.status=ACTIVE` 的班级数，去重 `class_id`）

**创建请求体**：

```json
{
  "username": "t9002",
  "displayName": "李老师",
  "password": "123456"
}
```

- `username`：本校唯一（`(school_id, username)`）
- `password`：明文入库 `{noop}` 前缀（与现网一致）
- 冲突：`40900` + `"用户名已存在"`

**停用教师**：直接切换 `status`；**不**要求先解除班级指派；`class_teacher` 行保留；**无法新登录**；已签发 token 在下次请求时由 `JwtAuthenticationFilter` 联查 `user.status` 返回 **40100**。

### 5.3 班级管理

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/admin/classes` | 本校班级列表；`?teacherUserId=` 可选（筛「含该教师的班」） |
| GET | `/admin/classes/{id}` | 班级详情 |
| POST | `/admin/classes` | 创建班级 + 教师指派 |
| PUT | `/admin/classes/{id}` | 更新 `name` / `status` / `teachers[]`（教师全量快照） |
| DELETE | `/admin/classes/{id}` | 删除（班内有学生 → `40020`） |

**列表/详情公共字段**：`id`, `name`, `code`, `status`, `studentCount`, `teachers`

**`teachers[]` 元素**：

```json
{
  "teacherUserId": 1,
  "teacherName": "演示教师",
  "role": "SUBJECT",
  "subjectName": "软件体系结构"
}
```

**创建请求体**：

```json
{
  "name": "软件工程 2026-2 班",
  "code": "SE2026-2",
  "teachers": [
    { "teacherUserId": 1, "role": "HEAD" },
    { "teacherUserId": 2, "role": "SUBJECT", "subjectName": "数据库原理" },
    { "teacherUserId": 3, "role": "SUBJECT", "subjectName": "软件体系结构" }
  ]
}
```

**更新请求体**：

```json
{
  "name": "软件工程 2026-2 班",
  "status": "ACTIVE",
  "teachers": [
    { "teacherUserId": 2, "role": "SUBJECT", "subjectName": "数据库原理" }
  ]
}
```

- `PUT` 必须携带 `teachers[]` 全量快照（仅改 `name`/`status` 时也须带上当前完整教师列表）。
- `code` 创建后**不可修改**（PUT 不接受 `code`）。
- `teachers` 至少 1 条；`teacherUserId` 不可重复。
- `role=HEAD` 时不得传 `subjectName`（传了也忽略并 canonicalize 为 `null`）。
- `role=SUBJECT` 时 `subjectName` 必填（trim 后非空）。
- `HEAD` 超过 1 人 → `40022` + `"每个班级最多只能有一名班主任"`。
- `SUBJECT` 缺 `subjectName` → `40023` + `"学科教师必须填写学科名称"`。
- `teachers` 为空 → `40024` + `"班级至少需要绑定一名教师"`。
- 班级编码冲突：`40900` + `"班级编码已存在"`。

### 5.4 学生管理

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/admin/students` | `?classId=` 可选；本校学生 |
| POST | `/admin/students` | 创建并分班 |
| PUT | `/admin/students/{id}` | 更新 `displayName` / `classId`（调班） |
| POST | `/admin/students/import` | 批量导入（与现网 Excel 模板一致） |
| POST | `/admin/students/{id}/status` | 启停 |

**列表项字段**：`id`, `username`, `displayName`, `classId`, `className`, `classCode`, `status`

**创建请求体**（与现网一致，逻辑迁至 admin）：

```json
{
  "username": "20260011",
  "displayName": "张三",
  "password": "123456",
  "classId": 1
}
```

**导入请求体**（与现网 `ImportStudentsRequest` 一致）：

```json
{
  "classId": 1,
  "rows": [{ "username": "...", "displayName": "...", "password": "..." }]
}
```

导入失败行 `reason` 文案与现网保持一致（如 `username already exists`）。

### 5.5 教师只读班级 API（收窄后）

删除：`POST` / `PUT` / `DELETE` 及 `ClassService` 中 `createClass` / `updateClass` / `deleteClass` 三个写方法（**不保留死代码**）。

### 5.6 删除的教师学生 API

## 13. 已否决方案（附录）

| 方案 | 否决原因 |
|------|----------|
| 第一期做平台超管 + 多校开通 | 超出第一期边界；单校 V13 即可验证组织模型 |
| 教师端保留建班建生 | 与「组织归校管」冲突 |

| 校管功能挂在教师端菜单下 | 角色与导航混杂，后期不可维护 |

| 组织 API 继续用 `/students` 仅改 `@PreAuthorize` | 路径语义混淆；`/admin/*` 边界清晰 |
