- **当前版本**：V7.2

- **性质**：跨 5 项需求、6 个阶段的**唯一决策源**。本文只写死跨阶段不可漂移的决策与边界；各期的 API 形态、表字段、页面落点、测试用例与验收步骤由该期独立 PRD / 技术方案写死，本文不替代。

- **范围结论**：平台超管是平台级操作者，学校组织与业务数据由本校 `SCHOOL_ADMIN` 管理；「给学校开通功能」= 按学校集合授权课件与题库（`content_share_grant`），不设功能开关 / 套餐模型；教师统一使用内容、不制作统一教材内容，教师自制课件为未来能力；学生「错题本」为后续独立能力，不纳入六期。**课件侧 V7.2 裁剪（D19 / D22）**：阶段 3 只由 `PLATFORM_ADMIN` 制作 / 发布 / 授权课件，`SCHOOL` / `TEACHER` 归属课件只保留模型字段、本期不产生数据、不交付入口；校管制作本校一套课件改为后续独立能力，不纳入 D15 六期；题目侧按 D10 / V7.1 原口径不变。

## 1. 已定决策清单

| 编号 | 决策点 | 唯一结论 |
|---|---|---|
| D01 | 角色模型与职责边界 | 新增第 4 个角色 `PLATFORM_ADMIN`（平台超管），定位为**平台级操作者**：开通 / 停用学校、创建首位校管、阶段 3 制作平台内容并按学校集合授权课件与题库。学校组织与业务数据由本校 `SCHOOL_ADMIN` 管理，平台超管不读取、不代管。「一个管理员管理多个学校」= 一个账号开通并维护多个学校租户；不引入 `SCHOOL_ADMIN` 多校关联表、不做跨校汇总报表 |
| D02 | 平台超管数据边界 | 平台超管无学校归属：`sys_user.school_id` 与 `CurrentUser.schoolId` 均为 `NULL`，取值一致、不按角色特判。JWT claims、`CurrentUser` 组件数、`user_login_session` 结构保持不变，三角色取值不变；平台超管相关测试必须显式传 `null` 构造 `CurrentUser`，不得用便捷构造（其默认 `schoolId=1L` 仅供三角色测试）。`audit_log.school_id`（`V18`）与 `http_access_log.school_id`（`V17`）可空，平台超管登录审计与业务操作审计一律写 NULL |
| D03 | 平台超管账号无学校归属 | `V25` 用 `${alterModifyColumn}` 放开 `sys_user.school_id` 的 `NOT NULL`（复用 `V18` 范式，不改 `FlywayPlaceholdersConfig`），平台超管种子行写 `school_id = NULL`；三角色历史行取值不变，`uk_sys_user_school_username(school_id, username)` 保持原样，不加部分索引 / 生成列 / DB CHECK。平台超管账号全局唯一由「仅迁移种子创建 + 不提供新增接口」保证（NULL 不参与唯一约束）；开放新增接口属 §6 非目标，本期及后续阶段均不引入额外索引 / 生成列 / DB CHECK。`JwtAuthenticationFilter` 直接取 `user.getSchoolId()` 构造 `CurrentUser`，不写按角色置 null 的分支。登录审计（`SecurityAuditEvent` / `logLoginFailure`）与业务操作审计均写 NULL，目标学校 id 写 `detail_json.targetSchoolId`。按 `school_id` 等值过滤的现有查询一字不改，NULL 行天然不匹配、不进入任何学校数据范围；未来新增按 `school_id` 分组的统计 / 报表须把 NULL 单列为「平台级」，不得并入任何学校分组，也不得给平台级账号补学校默认值。`DemoAccountProdGuard` 的 `WHERE school_id = 1` 不覆盖 NULL 行，必须显式覆盖 `school_id IS NULL` 且按用户名追加 `platform9001`（SQL 形态见 §5）。账号由迁移种子创建，不提供新增平台超管的接口 |
| D04 | 学校开通 / 停用 | 复用 `school.status`（`ACTIVE` / `DISABLED`）与全局唯一 `school.code`。开通学校时同时创建该校首位 `SCHOOL_ADMIN`，这是创建校管的唯一入口。停用只影响该校账号登录，不清数据、不删用户、不停用 `id=1` 演示学校、不改会话表 |
| D05 | 停用后的行为 | `DISABLED` 学校下所有账号登录返回 `40103`，文案沿用现网；停用演示学校返回 `40028`；学校不存在返回 `40400`；`40300` 保持现网越权语义 |
| D06 | 权限与鉴权 | 4 个角色的 `permissions` 以 1A PRD §4.2 的完整枚举为准。现有 6 个 admin controller 保持 `hasRole('SCHOOL_ADMIN')`，平台超管访问一律 403；新增学校管理 Controller 用 `hasRole('PLATFORM_ADMIN')`；教师端、学生端端点注解保持三角色原状。阶段 3 为 `PLATFORM_ADMIN` 追加 `CONTENT_WRITE` / `CONTENT_SHARE`、为 `SCHOOL_ADMIN` 追加 `CONTENT_WRITE`，教师 / 学生两组不变。**同名 `CONTENT_WRITE` 按端点分组生效、不按权限名全局生效**：课件侧制作 / 编辑 / 发布 / 下架 / 授权 / 挂载编辑端点一律类级 `hasRole('PLATFORM_ADMIN')`（D19 / D22）；`SCHOOL_ADMIN` 的 `CONTENT_WRITE` 只作用于题目侧端点（D19 题目侧生产者口径），**课件侧不产生任何写入端点与入口**；`PLATFORM_ADMIN` 的 `CONTENT_WRITE` 同时覆盖课件侧与题目侧 |
| D07 | 平台超管可达端点 | 平台超管只可达三类端点：登录、账号自身（个人信息 / 改密 / 登出）、平台级学校管理；阶段 3 追加平台内容端点。其余 `/api/v1/**` 由现有 `@PreAuthorize` 角色注解拒绝（403）。内容授权里的 `school_id` 是 `content_share_grant` 的数据字段，不是会话上下文。完整路径见 1A PRD §4.3 |
| D08 | 端点契约 | 新增学校管理端点由 1A 方案写死。现有三角色端点、登录响应字段、`/api/v1` 前缀、`ApiResponse` 与 `PagedResult<T>` 形态不变 |
| D09 | 前端入口 | 平台超管复用 `/admin` 壳层，不新建第四套壳层、不合并三套角色壳层。侧栏仅「学校管理」1 项，`/admin/schools` 是学校列表 / 开通 / 停用的**唯一业务入口**，`homePath` → `/admin/schools`。阶段 3 追加「平台内容」1 项。路由与导航细节见 1A PRD FR-6 |

| D12 | 目录与统一挂载 | 阶段 2 一次建成教材 / 教材小节 / 学校启用教材 / 课件 / 课件小节等目录表，阶段 3 / 4 只写数据与页面、不再建表；教材与课件按 D25 带学科归属列并支持同一学科下多条记录。挂载关系统一由 `content_mount` 多态多对多表承载（D23），挂载与可见性、授权、布置三者解耦（D24），且与学科归属正交（D25） |
