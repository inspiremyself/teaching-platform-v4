## 1. 背景与诉求

### 1.1 业务诉求

1. 教师每节课发布实验内容，包含若干子题（如「实验三：第 1 题 … 第 5 题」）。
2. 每道题有文字描述。
3. 学生对每个子题分别提交答案，支持**文字**与**截图（多图）**。
4. 教师汇总查看，并支持三种维度：
   - 按「某个实验」查看全班提交情况；
   - 按「某个学生」查看其历次实验提交；
   - 按「同一道题」查看所有同学的答案。

### 1.2 现状结论（调研）

| 能力 | 现状 |
|------|------|
| 实验 + 子题模型 | 已具备：`t_experiment` / `t_experiment_item` |
| 按子题分别作答 | 已具备：`experiment_answer` 唯一约束 `(submission, item)` |
| 文字作答 | 已接通：`answer_text` + `answer_json` |
| 多图 / 截图作答 | **未接通**：无上传 API、学生编辑器无图片、保存不写文件路径 |
| `answer_file_path` | 实验域为**预留死字段**（实体有、读写链路无）；作业域同名字段在用，勿混淆 |
| 按实验看全班 | 部分具备：`LabReports` 批改队列可按实验筛选，偏批改而非汇总矩阵 |
| 按学生看历次 | **缺口**：无教师侧「学生 × 跨实验」时间线 API/页面 |
| 按题看全班 | **部分缺口**：仅填空重判有分布；非通用答案墙 |

### 1.3 设计结论（一句话）

**不改核心表结构**：多图相对路径写入已有 `answer_json`；文件本体落本地磁盘（复用 `LocalFileStorageService`）；补齐上传/预览鉴权 API 与教师三种查看视图。`answer_file_path` **不 rename**，一期**一律不写**（保持 `null`），禁止冗余首图路径。

## 2. 目标与非目标

### 2.1 目标

1. 学生在 `TEXT` / `SHORT_ANSWER` 子题上可同时提交文字说明与 **0～5 张图片**（允许纯图或纯文字）。
2. 图片文件持久化到本地 `{FILE_STORAGE_ROOT}/lab-answers/{yyyy-MM-dd}/`，Compose 卷可保留。
3. `answer_json` 成为多图的主真相；教师/学生回显均从该结构解析。
4. 教师具备三种汇总查看路径（实验 / 学生 / 子题），数据均可由现有表 join 得出。
5. 下载与预览必须走鉴权接口，不暴露磁盘绝对路径、不做静态公开目录。

### 2.2 非目标

- 不引入 MinIO / S3 / CDN。
- 不把图片 base64 或 BLOB 写入数据库。
- 不把学生答题图复用为 `course_material` 资料记录。
- 不改造选择/填空/代码等客观题自动评分主链路（图片能力仅叠加在 `TEXT`/`SHORT_ANSWER`）。
- 不打破 `uk_experiment_submission (experiment_id, student_id)`：同一实验每名学生仍一条主提交。
- 本期不做实验报告导出 PDF、不做图片 OCR。
- 本期不写实验域 `answer_file_path`；不做孤儿文件清理、魔数校验、overview 导出、强制统一 WebP（Phase 3）。

## 3. 数据模型与关系

### 3.1 核心 ER（与诉求直接相关）

```text
sys_user / class_room / class_member
              │
              ▼
        t_experiment  ──1:N──►  t_experiment_item
        (Lab)                   (LabStep / 子题)
              │                        │
              │                        │
              ▼                        ▼
   experiment_submission  ──1:N──►  experiment_answer
   (LabSubmission)                  (LabStepAnswer)
   UNIQUE(experiment_id,            UNIQUE(submission_id, item_id)
          student_id)                    │
                                         ├─ answer_text
                                         ├─ answer_json   ← 多图主真相
                                         └─ answer_file_path  ← 死字段，一期恒 null
```

Java 映射：

| 表 | 实体 |
|----|------|
| `t_experiment` | `Lab` |
| `t_experiment_item` | `LabStep` |
| `experiment_submission` | `LabSubmission` |
| `experiment_answer` | `LabStepAnswer` |

### 3.2 关键字段语义

**实验 `t_experiment`**

- `experiment_id` / `experiment_name` / `class_id` / `created_by` / `status`
- `experiment_requirement` / `experiment_content`：实验说明类文本

**子题 `t_experiment_item`**

- `experiment_item_no`：第几题
- `experiment_item_name`：题目标题
- `experiment_item_content`：题目文字描述
- `question_type`：题型；**多图 UI 与保存校验仅允许 `TEXT`、`SHORT_ANSWER`**（入库/展示前将 `SHORT` 归一为 `SHORT_ANSWER`）；其它题型若带非空 `images` 则 400；`CODE` 不开多图

**提交 `experiment_submission`**

- 一名学生对一个实验一条记录
- `submit_status`：`SAVED` / `SUBMITTED` / `GRADED`
- `summary_text` / `summary_attachment_path`：整份实验小结（与子题多图分开）

**答案 `experiment_answer`**

- `answer_text`：兼容展示与评分用的纯文字
- `answer_json`：结构化 payload（含 `images[]`）
- `answer_file_path`：**本期不作为多图主存储**；读写链路均不触碰，恒为 `null`

### 3.3 三种教师查看的查询路径（模型已足够）

| 维度 | 查询思路 |
|------|----------|
| 按实验看全班 | 班级成员全员 LEFT JOIN `experiment_submission` → join answers / users |
| 按学生看历次 | `experiment_submission WHERE student_id=?` → 跨多个 experiment（限该教师可见实验） |
| 按子题看全班 | `experiment_answer WHERE experiment_item_id=?` → join submission / student |

**结论**：核心关系模型**已足够支撑诉求**；缺口在 API/UI 与图片读写链路，不在新建主表。

### 3.4 模型边界（必须认清）

1. **一题多图**：走 `answer_json.images[]`，不新增附件表（一期）。
2. **「历次」= 跨多个实验**：支持；**同一实验多版本正式提交**：当前唯一约束不支持，本期不做。
3. `lab_step_answer_log` / `experiment_blank_answer_override`：与多图汇总主链路无关，可忽略。

## 4. `answer_json` 多图契约

### 4.1 约定结构

在现有学生作答 draft / payload 体系上扩展（兼容 `kind: "text"`）：

```json
{
  "kind": "text",
  "text": "学生文字说明",
  "images": [
    {
      "path": "lab-answers/2026-09-04/8f3c2a1b-shot1.jpg",
      "name": "截图1.png",
      "contentType": "image/jpeg",
      "size": 245760
    },
    {
      "path": "lab-answers/2026-09-04/9a1d4e2c-shot2.jpg",
      "name": "截图2.jpg",
      "contentType": "image/jpeg",
      "size": 512000
    }
  ]
}
```

字段约定：

| 字段 | 必填 | 说明 |
|------|------|------|
| `kind` | 是 | 文字类固定 `text`（与现有 draft 一致） |
| `text` | 是 | 可为空字符串；保存时由服务端 canonicalize 为与 `answerText` 相同 |
| `images` | 是 | 数组；无图时为 `[]` |
| `images[].path` | 是 | **相对路径**，相对 `FILE_STORAGE_ROOT` |
| `images[].name` | 是 | 原始文件名，仅展示；上传接口原样回填 |
| `images[].contentType` | 是 | 落盘 MIME（与实际上传字节一致；前端压缩成功时多为 `image/jpeg`） |
| `images[].size` | 是 | 落盘后字节数 |

**作答完备性（写死）**：

| 文字 | 图片 | 判定 |
|------|------|------|
| 非空 | 0～5 | 已作答 |
| 空 `""` | 1～5 | 已作答（纯图） |
| 空 `""` | `[]` | **未作答**（`answered: false`） |

### 4.2 与 `answer_text` / `answer_file_path` 的关系

| 字段 | 职责 |
|------|------|
| `answer_text` | 纯文字副本；列表摘要、兼容旧评分路径；**以请求 `answerText` 写入** |
| `answer_json` | **多图 + 结构化作答主真相**；保存时 `text` 强制与 `answerText` 对齐 |
| `answer_file_path` | 不 rename；一期**禁止写入**，始终 `null`（与作业域同名字段语义隔离） |

**禁止**：在 `answer_json` 中存放 base64 图片数据。

### 4.3 兼容策略

- 旧数据无 `images` 字段：按 `images: []` 处理。
- 仅有文字的旧 `kind: text` payload：继续可 hydrate。
- 前端 `buildAnswerPayloadJson` / `hydrateDraftFromStep` 需识别并保留 `images`。

## 5. 文件存储方案

### 5.1 决策：本地磁盘

| 方案 | 结论 |
|------|------|
| **本地磁盘（采用）** | 与资料上传一致；`docker-compose` 已有 `file-storage` 卷；联调零外部依赖 |
| 对象存储 | 仓库无接入，一期过重（已否决） |
| DB BLOB / base64 | 接口与备份体积不可接受（已否决） |
| 复用 `course_material` | 语义是课程资料，不适合学生答题截图（已否决） |

### 5.2 存储根与目录

- 配置：`app.file-storage-root` ← `${FILE_STORAGE_ROOT:…}`
- Compose（路径 A）：`FILE_STORAGE_ROOT=/app/data/files`，卷 `file-storage:/app/data/files`
- 路径 B（本地 `test` profile）：**仓库根** `data/`（由 `scripts/path-b/backend.sh` 注入绝对路径；根 `.gitignore` 已忽略 `data/`）

```text
{repo}/
  data/
    h2/teaching_platform.*     # H2 文件库（路径 B）
    files/
      materials/...                 # 课程资料（既有）
      lab-answers/{yyyy-MM-dd}/...  # 实验答题图（本期）
```

| 目录（相对 `FILE_STORAGE_ROOT`） | 用途 |
|----------------------------------|------|
| `materials/` | 教师课程资料（`course_material`；既有，本期不改） |
| `lab-answers/{yyyy-MM-dd}/` | 学生实验答题截图（本期新增） |
| 项 | 结论 |
|----|------|
| 文件根 | `{repo}/data/files`（路径 B）或 `/app/data/files`（路径 A） |
| H2 文件库 | `{repo}/data/h2/`（仅路径 B；UT 仍用 mem） |
| 答题图子目录 | `lab-answers/{yyyy-MM-dd}/`（相对 `FILE_STORAGE_ROOT`；日期 = 上传当日 ISO `LocalDate`） |
| 落盘调用 | 校验通过后**原样** `LocalFileStorageService.store("lab-answers/" + yyyy-MM-dd, multipartFile)`（不重编码、不改字节） |
| 相对路径示例 | `lab-answers/2026-09-04/{uuid}-{originalName}`（扩展名随实际上传；前端压成 JPEG 时多为 `.jpg`） |
| 已否决 | `pictures/` 目录名；`lab-answers/` 平铺（无日期）；路径 B 落到 `backend/data/` |

### 5.3 上传约束（一期硬限制）

| 项 | 值 | 说明 |
|----|-----|------|
| 允许 MIME | `image/png`, `image/jpeg`, `image/webp` | 拒绝其它类型 |
| **落盘 / 上传单张大小** | **≤ 1 MiB** | 业务硬上限；后端超限直接 400，不压缩 |
| multipart 单文件上限 | ≤ 1 MiB | 与硬上限一致（不再为「先传后压」放宽） |
| 单题张数 | ≤ 5 | 前端 + 后端双重校验 |
| 最长边 | ≤ 1920 px | **仅前端压缩侧**约束；后端不读图、不校验像素边长 |
| 文件名 | 服务端 UUID 前缀 | 防覆盖与路径穿越（现有 store 已 normalize） |

须在 `application.yml` 增加（当前仓库尚未配置）：

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 1MB
      max-request-size: 8MB
```

### 5.4 超 1 MiB 自动压缩（仅前端；后端原样存储）

**决策**：单张图片**落盘必须 ≤ 1 MiB**。压缩只在前端做；后端**不做 Thumbnailator / ImageIO / 任何重编码**，校验 MIME + 字节大小后直接 `store`；超过 1 MiB 则 400，提示用户裁剪或换图后重试。

一期锁定实现：

| 层 | 选定方案 | 否决项 |
|----|----------|--------|
| 前端 | `browser-image-compression`，收敛到 `frontend/src/views/student/components/lab-answer/compressLabAnswerImage.ts` | 不手写散落 canvas 逻辑作为主路径 |
| 后端 | 校验通过后原样 `LocalFileStorageService.store` | **不引入** Thumbnailator；不以 JDK `ImageIO` 做压缩兜底 |

```text
选图
  │
  ├─ 前端：若 size > 1MiB 或 边长 > 1920
  │        → browser-image-compression（缩边 + JPEG 质量递减）直到 ≤1MiB 或达下限
  │        → 再发起 multipart 上传
  │        → 本地维护 compressed / originalSize，用于轻提示「已自动压缩」
  │
  └─ 后端：收到文件后
           ├─ MIME 白名单通过 且 size ≤ 1MiB → 原样 store（不重编码）
           └─ 否则 → 400，提示「图片过大，请压缩或裁剪后重试」
```

#### 前端压缩参数（写死）

| 参数 | 值 | 说明 |
|------|-----|------|
| 目标体积 | 1 MiB（1_048_576 字节） | 与业务上限一致 |
| 最大边长 | 1920 → 1280 → 1024（阶梯） | 先缩边再降质 |
| 输出格式 | **前端压缩成功时输出 JPEG**（`image/jpeg`） | PNG/WebP 压成 JPEG；未超限且无需缩边的原图可保留原 MIME 上传 |
| 质量阶梯 | 0.85 → 0.75 → 0.65 → 0.55 | 到下限仍超限则失败，不发起上传 |
| 动画 / 多帧 | 不支持 | 仅静态图 |

#### 职责划分

| 层 | 职责 |
|----|------|
| 前端 | 上传前自动压缩；本地记录 `compressed`/`originalSize` 并提示「已自动压缩」 |
| 后端 | **只校验不压缩**：MIME + `size ≤ 1 MiB`，通过则原样落盘 |
| `answer_json.images[].size` | 记录**落盘后**字节数（与上传字节一致） |

#### 与验收相关的行为

1. 原图 3 MiB 手机照片：前端应能压到 ≤ 1 MiB 再上传并成功落盘。  
2. 极端大图（前端压不下去）：前端报错且不发起上传；若绕过前端直接传 >1 MiB，后端 400 且不落盘。  
3. 已 ≤ 1 MiB 且最长边 ≤ 1920 的图：前端不强制重编码；后端原样存储。

### 5.5 孤儿文件策略（一期）

- 学生删除某张图并再次 `saveAnswer`：JSON 不再引用该 `path`。
- **一期**：不删盘上孤儿文件；同步清理划入 Phase 3（本期非目标）。
- `./scripts/path-a/down.sh --volumes` 会清空 Compose 卷内文件，运维文档已有提示，保持即可。
- 路径 B 清空答题图：仅删除 `{repo}/data/files/lab-answers/`（不要误删整个 `files/` 以免伤及资料）；清空库数据：删除 `{repo}/data/h2/` 后重启后端。

## 6. API 设计

统一前缀 `/api/v1`，响应结构保持 `code/message/data/timestamp`。

### 6.1 学生：上传答题图片

```http
POST /api/v1/student/labs/{labId}/answers/{stepId}/images
Content-Type: multipart/form-data
Authorization: Bearer <token>

file: <binary>
```

**权限**：`STUDENT`；须能访问该已发布实验；实验未关闭；提交状态非 `SUBMITTED`/`GRADED`；子题类型为 `TEXT` 或 `SHORT_ANSWER`（含 `SHORT` 归一）。

**成功 `data` 形状（字段均必返回）**：

```json
{
  "path": "lab-answers/2026-09-04/8f3c2a1b-shot1.jpg",
  "name": "截图1.png",
  "contentType": "image/jpeg",
  "size": 820144
}
```

说明：

- 后端**不压缩**：校验 MIME + `size ≤ 1 MiB` 后原样落盘；`size` 为落盘字节数。
- `compressed` / `originalSize` **不上报后端**；由前端在选图压缩后本地维护，用于提示「已自动压缩」。
- 接口**不单独改** `experiment_answer`；正式写入仍走保存答案接口，由前端把 `images` 编入 `answerPayloadJson`。

### 6.2 学生：保存子题答案（扩展既有）

```http
POST /api/v1/student/labs/{labId}/answers/{stepId}
```

请求体保持：

```json
{
  "answerText": "文字说明",
  "answerPayloadJson": "{\"kind\":\"text\",\"text\":\"文字说明\",\"images\":[...]}"
}
```

服务端校验与写入（写死）：

1. 子题非 `TEXT`/`SHORT_ANSWER` 时，`images` 必须为 `[]`，否则 400；
2. `answerPayloadJson` 可解析；
3. **以 `answerText` 为准**：写入 `answer_text`；canonicalize 时强制把 `payload.text` 改成与 `answerText` 相同（即使请求里二者不一致也**不 400**）；
4. `images.length ≤ 5`；
5. 每个 `images[]` 必须含 `path` / `name` / `contentType` / `size`；
6. 每个 `path` 必须匹配 `^lab-answers/\d{4}-\d{2}-\d{2}/`（禁止平铺 `lab-answers/{file}`），规范化后落在 storageRoot 内，且**磁盘文件存在**（防伪造未上传 path）。

### 6.3 学生/教师：预览或下载图片（鉴权）

一期只实现这一种形态：

```http
GET /api/v1/labs/answer-images?path=lab-answers%2F2026-09-04%2F8f3c2a1b-shot1.jpg
```

服务端校验：

- 调用者是该答案所属学生本人，或**对该实验具备与 `listTeacherReports` / 报告详情相同的教师可见权限**（本班实验教师；**不**硬绑 `created_by`）；
- `path` 规范化后仍在 `storageRoot` 下；
- 必须匹配 `^lab-answers/\d{4}-\d{2}-\d{2}/`（与保存校验一致；禁止 `materials/` 等其它前缀）。

响应：`image/*` 字节流 + 合适 `Content-Type`。

前端展示（写死）：用 `frontend/src/utils/request.ts` 带 Token 拉取 blob，再 `URL.createObjectURL` 赋给 `<img>`（对齐资料下载模式）。禁止把裸相对路径塞进 `src`；禁止 query-token；禁止返回 `file://` 或宿主机绝对路径。

  "classId": 1,
  "items": [
    { "stepId": 2001, "stepNo": 1, "title": "第1题" }

    {
      "studentId": 3,

      "submissionId": 5001,

      "submittedAt": "2026-09-04T10:00:00+08:00",

### 7.2 保存流程（伪代码）

```text
saveAnswer(labId, stepId, request):
  校验学生权限与实验状态
  确保 LabSubmission 存在且可编辑
  payload = parse(request.answerPayloadJson)
  payload.text = request.answerText          // canonicalize，不因不一致而 400
  validateImages(payload.images)             // 题型、lab-answers/yyyy-MM-dd 形态、数量、元数据齐全、磁盘存在
  answer.answerText = request.answerText
  answer.answerJson = canonicalize(payload)
  // answer.answerFilePath 保持 null，不赋值
  save answer + append log(answerText)
```

### 7.3 安全

- 所有文件 IO 必须 `normalize` 后 `startsWith(storageRoot)`（现有工具已具备）。
- 预览接口必须做「人-题-实验」归属校验，防止枚举 `path` 越权读他人截图；教师侧权限对齐报告可见性。
- 上传一期仅校验声明 MIME + 扩展名白名单；文件头魔数校验划入 Phase 3。

### 7.4 测试要求

- `LabService` / Controller 测试：
  - 上传合法图片（≤1 MiB）原样落盘并返回相对路径与元数据；>1 MiB 或非法 MIME 被拒绝且不落盘；
  - 保存含多图 payload 后详情可回读；`answerText` 与 payload.text 不一致时仍成功且 json 被改写对齐；
  - 伪造 `path`（如 `../`、`materials/...`、`lab-answers/no-date.jpg` 或引用不存在文件）被拒绝；
  - 非文字题带非空 `images` 被拒绝；
  - 教师 overview（含未交班级成员）/ 学生历次 / 子题答案墙权限与数据正确；

## 11. 风险与对策

| 风险 | 对策 |
|------|------|
| 磁盘被大图打满 | 落盘单张 ≤ 1 MiB（前端先压 + 后端拒超限）+ 张数上限；后续可加配额 |
| 压缩损失关键细节 | 最长边保 1920 起压（仅前端）；已 ≤1MiB 不重编码；失败时允许用户自行裁剪重传 |
| 绕过前端直传大图 | 后端 `size ≤ 1 MiB` 硬拒绝；multipart `max-file-size: 1MB` |
| path 伪造越权 | `^lab-answers/\d{4}-\d{2}-\d{2}/` 形态校验 + storageRoot 校验 + 磁盘存在 + 归属校验 |
| Compose 清卷丢文件 | 使用 `./scripts/path-a/down.sh` 默认保留卷；勿随意 `--volumes`；DB 路径失效需可容忍提示 |
| 路径 B 重启丢图/丢库 | 上传文件在 `{repo}/data/files/`，库在 `{repo}/data/h2/`（文件模式，默认保留）；勿与 mem 混淆；勿再使用 `backend/data/` |
| 与作业 `answer_file_path` 混淆 | 文档与代码评审明确实验多图只认 `answer_json.images`；实验域该列恒 null |
| 客观题误开多图 | UI 仅对 `TEXT`/`SHORT_ANSWER` 展示上传；后端同白名单，非空 `images` 直接 400 |
| `<img>` 不带 JWT | 统一 blob + `request` Token，禁止裸 src |

6. `./mvnw test` 中实验相关用例通过；路径 A / 路径 B 可演示上传—保存—报告预览主链路。

## 14. 附录：为何不 rename `answer_file_path`

1. 实验域该列当前无读写主链路，rename 只增加 migration 噪音。  
2. `VARCHAR(255)` 改名为 `*_json` / `*_paths` 会造成类型语义与作业同名字段进一步混乱。  
3. 多图主真相放在已有 `answer_json` 更干净，且与现有结构化作答一致。

### 14.1 已否决方案（勿再实现）

| 否决项 | 原因 |
|--------|------|
| `lab-answers/` 平铺（无日期子目录） | 必须按日分目录 `lab-answers/{yyyy-MM-dd}/` |
| `pictures/{yyyy-MM-dd}/` | 目录名改回 `lab-answers/`，语义贴实验答题 |
| 路径 B 数据落在 `backend/data/` | 统一仓库根 `data/`；脚本注入绝对路径 |
| `answer_file_path` 冗余写首图 | 双真相；与作业同名字段易混 |
| 前端手写 canvas 作主压缩路径 | 质量阶梯与边界情况更易漏；统一 `browser-image-compression` |
| 后端 Thumbnailator / `LabAnswerImageCompressor` 兜底压缩 | 本期明确后端只校验原样存储；压缩责任全在前端 |
| 后端裸 JDK `ImageIO` 作压缩 | 同上；不引入服务端重编码 |
| 压缩输出强制统一 WebP | 兼容性与编码复杂度；前端压缩成功时用 JPEG 即可 |
| 预览 `.../answer-images/{labId}/{stepId}/{fileName}` | query `path` 更简单且与存储相对路径一致 |
| 预览权限硬绑 `created_by` | 与报告可见性不一致；共班教师会 403 |
| `answerText`≠`payload.text` 时 400 | 双源易误伤；改为 canonicalize 以 `answerText` 为准 |
| 总览入口挂 `Labs` / 顶栏新菜单 | 汇总与批改同属报告域，挂 `LabReports` |
| 历次入口挂 `Students` 行操作 | 本期唯一从总览下钻，避免双入口 |
| 答案墙从 `LabSteps` 进入 | 配置页与汇总查看语义冲突 |
| 跳转 `report-view/{studentId}` | 统一走已有 `lab-reports/{submissionId}` |
| 并列 `ImageAnswerEditor` | 文字题就地扩展更贴现有 `LabSteps` 用法 |
| 矩阵只列已有 submission | 未交学生不可见；必须班级全员 |
