# 自查并修正

对**技术方案文档**或**代码实现**做多轮自查 → 修复 → 再自查，直到**本轮新发现问题点收敛**（≤2，最好为 0）。收敛标准与 `feature-dev-workflow.mdc` 一致。

## 0. 判定模式（必须先做）

根据**上一轮对话主任务**（不是用户最新一句里的单个词）选一条路径：

| 模式 | 触发信号（满足任一） |
|------|----------------------|
| **方案模式** | 上一轮在起草/修订 `docs/技术方案/*.md`；用户说「自查方案」「审阅方案」「方案定稿前检查」；尚无对应实现 diff |
| **实现模式** | 上一轮在改前后端/测试代码；用户说「对照技术方案自查实现」「实现自查」；git diff 或对话中已有方案对照编码 |

**无法判定时**：若存在未收敛方案且用户未开写码 → 方案模式；若已有实现改动且存在已定稿方案 → 实现模式；仍不清则向用户确认一句。

**不要**在同一轮里混做方案+实现大改；实现模式发现方案缺口时，先最小回写方案再改码。

---

## 1. 收敛规则（两模式通用）

每轮只统计**本轮新发现**的问题点（上轮已修的不重复计）。

| 本轮新发现问题点 K | 动作 |
|-------------------|------|
| K = 0 | ✅ 收敛，结束 |
| K ≤ 2，且均为非阻塞项且已修复/记入修订记录 | ✅ 收敛，结束 |
| K > 2 | ❌ 修复全部后**必须**开下一轮 |
| 需用户拍板 | ❌ 写入方案「待确认」，停下，不算收敛 |

**非阻塞项**：措辞、修订记录、示例微调。**阻塞项**：API/状态机/鉴权/入口/验收不可测/决策清单缺口/与现网矛盾。

每轮结束前**必须**用下方模板向用户汇报；方案模式同步写入 §修订记录。

---

## 2. 方案模式

**必读**：`tech-spec-decisive.mdc`、目标方案全文、`feature-dev-workflow.mdc` §1.1。

### 每轮动作

1. 对照 `tech-spec-decisive.mdc` 定稿自检 + **决策清单**逐行（入口、API、鉴权、边界、验收、非目标）。
2. 对照**现网代码**（相关 controller、页面、迁移）：假设是否与仓库一致。
3. 全文搜索实现路径歧义：`或` / `二选一` / `推荐` / `待定` / `可挂在`（涉及实现路径的须写死）。
4. 列出**本轮新发现问题点**（编号）。
5. **当场修文档**；开放项写进「待确认」或「非目标」。
6. 按 §1 判定是否收敛；收敛则文首改 **已定稿（决策写死，可直接编码）**。

### 方案轮次输出模板

```text
方案自查第 N 轮
- 新发现问题点：K 个
  1. …
  2. …
- 已修复：…
- 结论：未收敛（K>2，继续下一轮）/ 已收敛（K≤2 或 K=0）
```

---

## 3. 实现模式

**必读**：对应已定稿方案（决策清单 + 测试计划 + 验收标准）、`feature-dev-workflow.mdc` §2.1、相关文件 **git diff**。

### 每轮动作

1. **决策清单逐行勾选**（不是扫一眼）。
2. 对照 diff 扫高频漏项：契约、前端交互、异步竞态、资源生命周期、边界、范围外、测试用例名/错误文案/JavaDoc。
3. 列出**本轮新发现问题点**（编号）。
4. **修复本轮全部**（方案缺口 → 先回写方案；bug → 最小 diff）。
5. 按 §1 判定；收敛后若尚未跑验证，提示进入 `feature-dev-workflow.mdc` §3（build/test），但**本技能不要求**在本轮内跑全量验收，除非用户明确要求。

### 实现轮次输出模板

```text
实现自查第 N 轮
- 对照方案：<方案文件名>
- 新发现问题点：K 个
  1. …
  2. …
- 已修复：…
- 结论：未收敛 / 已收敛
```

---

## 4. 反例

- ❌ 只自查一轮就宣称收敛
- ❌ K>2 仍说「差不多了」
- ❌ 不列问题点编号，只口头说「没问题」
- ❌ 实现模式发现方案错误却直接改代码不改方案
- ❌ 把上轮已修问题重复计入本轮 K
